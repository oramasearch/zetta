# The #969 loop walked in one thread on a live node (2026-10-21)

**Issue:** [#969](https://github.com/oramasearch/zetta/issues/969) step 4, *measure what the
current checkpoint can actually drive*. **Related:** [#975](https://github.com/oramasearch/zetta/issues/975).

**What was tested.** A headless node built from branch `feat/969-chat-proposes-run` (commit
`711412a4`, on `dev` at `e9587213`), driven over REST in one thread, with the real base-agent
checkpoint `base-agent-0.6b-interaction-v16` (CPU decode, no MLX; the host was under a load
average of about 40). A baseline of the same steps ran on a node built from `dev` at `e9587213`.

**Data.** No customer data. 400 synthetic accounts (`account_id`, `support_tickets`,
`tenure_months`, `monthly_spend`, `failed_payments`, `churned`; every 17th label flipped),
generated by the script below and landed as `walk.accounts`.

This is an internal validation report, filed here rather than in [`results/`](results/README.md),
which holds client-facing reports.

## How it was run

```sh
./build/bin/zetta --headless --data-dir <scratch>/data \
    --mcp-listen 127.0.0.1:4871 --listen 127.0.0.1:7871 --admin-token <token>
# then, over REST with the owner bearer:
POST /v1/upload_dataset   {database: walk, table_name: accounts, format: csv, content: <400 rows>}
POST /v1/create_agent     {name: "Ask Orama", model: <checkpoint v16>,
                           tools: [get_run_report, explain, score, get_model, list_projects]}
POST /v1/chat             {agent, message: "Set up a churn project on my accounts and tell me which
                           accounts are most at risk.", dataset_path: walk.accounts, holdout_fraction: 0.25}
GET  /v1/list_projects
POST /v1/approve_run_proposal {proposal_id}      # then poll GET /v1/get_run
GET  /v1/get_run_report   {run_id, limit: 5}
POST /v1/chat {agent, message: "Which accounts are most at risk?"}
POST /v1/chat {agent, message: "Why is the top one at risk?"}
POST /v1/chat {agent, message: "What would account 5267 score if it had half the support tickets?"}
POST /v1/chat {agent: <same checkpoint, no tools>, message: <the first ask again>, dataset_path: walk.accounts}
```

The dataset generator: `account_id = 5000+i`, `support_tickets = (7i) mod 11`,
`tenure_months = 1 + (13i) mod 72`, `monthly_spend = 19 + 0.75·((37i) mod 400) + 0.01·(i mod 7)`,
`failed_payments = (5i) mod 4`, `churned = [0.3·tickets + 0.8·failed − 0.04·tenure > 1.5]`,
flipped when `i mod 17 = 0`, for `i` in 0..399.

## Which legs the model drives itself

| Leg | Driven by the model? |
|---|---|
| Ask → proposal | **Yes.** The checkpoint declares `action` for a build ask, and the engine turns that into a proposal with a preview. Enabling five introspection tools did not stop it building (5 steps on both builds). |
| Approve → run → report | Not a model step: the person approves, the engine runs and reports. Works. |
| Follow-up finds its referent | **Yes, by the engine.** Every follow-up grounded on the Project that just ran (`grounded_project`), with nothing in the sentence naming it. |
| Introspection (`get_run_report`, `explain`, `score`) | **No.** The model reaches for the right tool name (`score` for "most at risk", `explain` for "why") but emits it with no arguments, inside an `answer` envelope, and never calls `get_run_report`. Its replies then state figures nothing computed. These legs work when the capability is called directly (the journeys in `tests/api/test_chat_loop.cpp`) and do not work when the model is left to call them. |

That is the expected shape for a checkpoint never trained on these tools or on the post-run
follow-up, and it is what #969 steps 5 and 6 (the corpus families and the retrain) are for.

## Findings

Each is filed; the fix lands with its layer-1 journey (the promotion rule in `docs/testing/mcp-journeys.md`).

1. **Introspection tool calls arrive without arguments, inside a final answer** ([#1374](https://github.com/oramasearch/zetta/issues/1374)). A tool call in an
   `answer` envelope is executed after the reply is already written, so even a correct call could
   not inform the reply. Training (steps 5–6) and possibly the harness.
2. **After a run, a new build ask is answered instead of built** ([#1375](https://github.com/oramasearch/zetta/issues/1375)). With no project named, `chat`
   grounds on the latest run, and the grounded prompt moved the same ask from `action` to `answer`
   (the control turn).
3. **The proposal's steps and the turn's Pipeline disagree** ([#1376](https://github.com/oramasearch/zetta/issues/1376)). The turn shows the 5 steps the model's
   tool calls built; the proposal (what approval will create) carries the 7-step M-1 template the
   engine compiled. Both are shown to the person.
4. **The Studio surfaces do not render a proposal** ([#1377](https://github.com/oramasearch/zetta/issues/1377)). Approving is an API/MCP call today; the Ask
   Orama rail and the Chat screen show neither the preview nor approve/reject.

## What was fixed on the way

The four found before this walk are fixed in the same change and covered by tests: `POST /v1/chat`
(#975), the live tools that never reached the registry (dropped in `b5ca4290`), the build steps
reported as `unknown_tool`, and the missing propose/approve leg.
