# v0.3.0

**Released:** 2026-10-17 · **Branch:** `dev` · **Previous:** [`v0.2.0`](https://github.com/oramasearch/zetta/releases/tag/v0.2.0) (2026-10-12)

`v0.2.0` was the engine a hosted workspace runs on. `v0.3.0` is its part of secure
networking ([orama-bridge#186](https://github.com/oramasearch/orama-bridge/issues/186)):
a workspace Zetta now keeps the workspace's network history, gives each app connection its
own scoped credential, and joins Zetta nodes in separate private networks through
zetta-tunnel peer gateways. The mutual-TLS and framing code the cluster uses is now a
library that zetta-tunnel links too.

Six pull requests since `v0.2.0`: four features (#1284, #1285, #1286, #1287), the release
procedure (#1278), and the merge of `main` back into `dev` after `v0.2.0` (#1279). Five
commits and 53 files before this release's own change.
The generated OpenAPI has **176** `/v1` paths (was 172), and the test sources hold 2,992
test cases (was 2,977).

---

## Behaviour changes

There is no behaviour change that a `v0.2.0` caller has to adapt to. Two things are new at
startup and in the permission vocabulary:

- **A node declares four network record collections when it starts**, and refuses to start
  if it cannot (`zetta: cannot initialize network record collections: ...`). The
  declarations are idempotent and byte-identical on every node.
- **Two permission atoms are added**, `network:read` and `network:write`. The canonical
  vocabulary has 34 atoms (was 32). No built-in role is changed.

The cluster's inter-node protocol is unchanged: the handshake order, wire bytes, frame
bound and plaintext mode are the same as in `v0.2.0` (#1284). A cluster with nodes of both
versions was not tested.

## Added

### Workspace network records — #1281

The records people inspect about a workspace's network live in that workspace's Zetta;
Lake's Postgres keeps only the desired state the operator enforces.

| Record type | Collection | Retention |
|---|---|---:|
| `connection` | `network_connections` | 365 days |
| `grant` | `network_grants` | 365 days |
| `tunnel_session` | `network_tunnel_sessions` | 90 days |
| `activity` | `network_activity` | 30 days |

- **`write_network_record`** (REST and MCP) takes the producer's record as it is: Lake's
  connection and grant lifecycle snapshots, and zetta-tunnel's relay session, refusal and
  egress, peer, ingress and mesh decision records. It waits for the owner's fsync and for
  every reachable live peer to install the write, and needs `network:write`.
- **`list_network_records`** reads a type newest first, or by one of its indexes (event,
  workspace, ids, role, decision, rule), with a page cursor. It needs `network:read`.
- A tunnel session's start and end share one key, so the end replaces the live row with
  its final byte totals. Other records are keyed by the SHA-256 of their canonical JSON,
  so an identical retry is idempotent.
- The JSON format is `zetta.NetworkRecord` version 1, published as
  `schemas/network_record.schema.json`. Unknown fields and malformed identifiers are
  refused before storage.
- Neither permission grants the generic record API.

See [`docs/network/network-records.md`](../network/network-records.md).

### Scoped app credentials — #1280

An app reaching a workspace Zetta no longer inherits workspace-wide access.

- **`issue_app_credential`** turns a connection's `credential_scope` (`read` or `write`;
  a database, tables, topic prefixes) into a connection-owned user and least-privilege
  role, and returns a bearer credential **once**. Only its salted hash is stored. A second
  live credential for the same connection is a `conflict`. It needs `tokens:manage`.
- **`revoke_app_credential`** revokes every token of that connection and removes its role
  assignment. Repeating it answers `revoked: 0`, so an operator can reconcile absence.
- `read` grants SQL reads on only the named database or tables, and topic reads and
  receives on only the named prefixes. `write` adds SQL writes and publish, update and
  delete-event rights on the same resources. Neither grants DDL, user or token
  administration, topic creation or deletion, or network records.
- Every use goes through the existing registry checks and audit trail; revocation fails
  authentication immediately.

See [`docs/network/scoped-app-access.md`](../network/scoped-app-access.md).

### Zetta peer links through peer gateways — #1282

Zetta nodes in separate private networks form one cluster through zetta-tunnel peer
gateways. A node points `--peer` at its local import listener and runs `--dial-out-only`,
so it advertises no private address that could collide with another cluster's pod range.
Zetta's own mutual TLS 1.3 stays end to end: the gateways copy bytes and never hold the
join token.

`PeerGateway.OverlappingPrivateNodesReplicateThroughOpaqueGateways` proves it with two
nodes on the same modelled private address and two opaque forwarders: one cluster forms,
and CRDT writes on either node converge. See
[`docs/network/peer-gateway-links.md`](../network/peer-gateway-links.md).

### The transport library — #1283

`zetta::transport` (`zetta_transport`) is the cluster's mutual-TLS and framing code as a
library of its own:

- PEM credential loading, and checks before a connection starts: the key matches the
  leaf, the leaf verifies against the CA bundle now, and no system trust anchor is added;
- a Corosio context that is TLS 1.3 only and verifies the peer in both roles;
- `FramedStream`, newline-framed reads and writes with a frame bound.

`-DZETTA_TRANSPORT_ONLY=ON` configures only the library and its direct dependencies (Capy,
Corosio, OpenSSL), static or shared, so zetta-tunnel can `add_subdirectory` it. Zetta's
cluster uses the same target. See
[`docs/cluster/transport-library.md`](../cluster/transport-library.md).

### The version, held by a test

`project(VERSION)` in `CMakeLists.txt` now says the release version (it said `0.0.1`, a
known issue of `v0.2.0`). `tests/test_release.cpp` reads `kVersion` from
`include/zetta/version.hpp` and checks that it equals the CMake project version, the
committed `schemas/openapi.json` `info.version`, and that this page exists and is listed
in the index.

**Before this tag, the post-`v0.2.0` tree has not run on a cluster.** On 2026-10-17 every
Zetta on the development cluster (`orama-production-cluster-01`: the Lake bus
`lake/lake-prod-zetta-zetta-0` and four workspace Zetta pods) runs
`oramasearch/zetta:main-4015ef76`, which is `v0.2.0`. The new capabilities were exercised
by the test suite only, in-process, with real Corosio TCP and mutual TLS between nodes.

`Lake` resource.

## Known issues

Security first. These are open in the tracker; none is new in this release.

- **[#819](https://github.com/oramasearch/zetta/issues/819), [#793](https://github.com/oramasearch/zetta/issues/793)**
  — some malformed SQL (a malformed table reference, `REVOKE TOKEN`, a scoped
  `GRANT ON table(cols)`, `SELECT current_user()`) was reported to throw an uncaught
  `ParseError` that ends the node: a denial of service by anyone who can send SQL. On the
  macOS build of this release, `SELECT * FROM system.*`, `REVOKE TOKEN abc`,
  `GRANT sql:read ON t(a,b) TO x` and `SELECT current_user()` over `/v1/sql` each answer
  `engine_error` and the node stays up (checked 2026-10-17). #793 names a toolchain
  miscompile as the cause, and the Linux image (Clang 19) was not checked, so both stay
  open.
- **[#760](https://github.com/oramasearch/zetta/issues/760)** — column masking can be
  bypassed with an aggregate (`SELECT id, MAX(salary) ... GROUP BY id`).

  — mutual-TLS gossip can stall because the read and write pumps share one OpenSSL
  stream, and a node can silently stop applying inbound sync. The transport moved into a
  library in this release without changing that behaviour.

## Upgrading

1. **No migration.** A `v0.2.0` data directory starts as is; the node adds the four
   network record collections on first start.
2. **Grant `network:write` to zetta-tunnel and `network:read` to Lake's service role**
   (each with `mcp:call`) before they write or read network records.
3. **Grant `tokens:manage`** to whoever issues app credentials.
4. Upgrade every node of a cluster together, as for `v0.2.0`: mixed versions were not
   tested.
