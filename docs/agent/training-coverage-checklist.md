> **Status update (2026-07-23) — the NATIVE generator now covers the full plan.** The base-agent
> corpus is generated natively in Zetta by `BaseAgentDatasetGenerator` (#873/#878) from
> `plan_solution_templates()` (`src/core/dataset/plan_templates.cpp`). Verified live via
> `generate_dataset base-agent`: **40 gated subjects, all admitted** — churn, search, the
> supervised solutions (S-2…S-12), **every method M-10…M-21** (the 11 that had zero coverage),
> the remaining use cases (UC-13…24), the data supply chain (DSC), autonomy (AC), and ABSTAIN.
> Adding a subject is one row in the template table. The section below is the **historical**
> analysis of the offline Python corpus (`data/base-agent-training-set.jsonl`) that motivated the
> native generator; the native generator is now the source of truth. Remaining polish: even
> per-subject variant counts + a held-out canary of unseen combinations.

---


**What this is.** A checklist of every subject in the solutions-designs plan
(`modules/solutions-designs/docs/plan/`) against whether it is integrated into the
base-agent training corpus (`data/base-agent-training-set.jsonl`, 565 tasks, generated by
`scripts/gen_base_corpus.py` grounded via `scripts/build_catalog.py`). It is the gap map that
drives extending the corpus to cover the whole plan **and all possible paths**.

**How coverage was measured.** Regex over every task line for each subject's id (`\bM-7\b`,
`\bC-3\b`, `\buc9\b`, …). Counts undercount name-only references (a churn task rarely carries
the literal `uc1` tag), so a low count with a known anchor is annotated. Legend:

- ✅ **integrated** — well represented (≥ ~10 tasks, or a hardcoded family)
- 🟡 **thin** — present but under-covered (1–9 tasks)
- ❌ **missing** — zero tasks reference it

> **Structural note (the bigger change this checklist serves).** The corpus today trains the
> agent to emit the **solution *facts*** (the gate's `info.checks`). Per the 7/21 architecture
> + blender-rl, the agent's real action is `{message, tool_calls, execution_graph}` and the
> facts are the **verifiable reward** on the *run* pipeline (active-weight renormalized per use
> case — so each pipeline's shape follows its use case, not a fixed six stages). Extending
> coverage (below) and reshaping the output are the same effort. See
> [inference-runbook.md](inference-runbook.md), [training-runbook.md](training-runbook.md),
> and blender-rl's `docs/dataset_strategy.md` (grow by generation, gate by verification).

## 6. Output-format status (the reshape)

| Field | Today | Target (7/21 architecture + blender-rl) |
|---|---|---|
| Agent output | the solution **facts** (JSON) | `{message, tool_calls, execution_graph}` (the **action**) |
| Reward | exact-match on facts | **run** the pipeline → gate `info.checks`, active-weight renormalized per use case |
| Discrimination | reference + negative controls (facts) | reference + negative-control **pipelines** that fail the gate |
| System prompt | none baked in (drifted) | Studio Auto-AI identity baked into every example, à la blender-rl |

## 7. #853 — the per-customer fork loop (the customer side of the same RLVR loop)

The base agent (this corpus) is **forked per customer** and keeps learning on **their** data:
the fork runs the execution graph in the customer's *real* environment; it **may fail** (schema
drift → broken SQL); the RLVR loop trains the fork on **their experience** (their queries,
their outcomes) — the "never stops learning" of the 7/21 transcript. Status:

| Piece | Status |
|---|---|
| Base corpus (seeds the fork) | this checklist |
| RLVR step (`grpo_step`) over the native grader | exists in `zetta-core` (needs the run-in-env reward wired) |
| Fork + per-customer post-training loop (#853) | not built — the next phase |
| Run-and-score against the customer's environment | the reward substrate #853 needs |

## 8. The generators — Python today, native C++ next

Current generators are Python (`scripts/gen_base_corpus.py`, `gen_autosuggest_corpus.py`,
`build_catalog.py`), run offline with `uv`. They need **updating** for the reshape (emit
`{message, tool_calls, execution_graph}` + the Studio system prompt + full-plan coverage) — and
then **porting to native C++ inside Zetta** (ADR-17, no foreign runtime in the product path).
Why native: **#853's per-customer fork must generate training data from the customer's *own*
environment** — scan their schemas, mine their real queries/outcomes, synthesize tasks against
*their* data, gate by running in *their* environment. A Python script can't run inside the Zetta
binary or the customer's cluster; the generator is a product capability, not an offline tool.
The Python generators stay as the offline seed/reference until the native path lands.

## 9. The extension plan (what to add, in order)

1. **Reshape the output** — corpus emits `{message, tool_calls, execution_graph}`; facts become
   the gate checks; negative controls become failing pipelines. Bake the Studio system prompt in.
   Update the Python generators to this shape first.
2. **Fill the Band-A core** — raise UC-8/10/11/12/13 and their solutions S-1…S-12 to ✅ with
   real, runnable reference pipelines (dogfood: churn + search first).
3. **Fill the method gaps** — author the 11 ❌ methods (M-10 NLP/RAG and M-16 optimization first),
   each with its own gate checks (difficulty lives in the checks).
4. **Add the missing subjects** — the data supply chain (DSC-1…8) as pipeline stages, autonomy
   classes (act-under-approval), the full gate check catalog, a held-out canary of unseen combos.
5. **Port the generator to native C++** — a Zetta capability that synthesizes + gates the corpus
   inside the engine, so a customer instance can grow its own.
6. **Wire #853** — the fork + run-in-environment RLVR reward, so the customer's agent learns
   from their experience (uses the native generator over their data).
