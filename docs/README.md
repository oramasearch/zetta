# zetta docs

zetta is a database. A *zetta node* is one running instance; it runs **headed**
(default — with an SDL3 + Dear ImGui UI) or **headless** (no UI, for servers).
This directory documents the system; keep it in sync as the system changes.

- [orama-zetta.md](orama-zetta.md) — **read first**: what Orama Zetta is and the working product decisions (naming, value-first messaging, AI projects as the central item, the use-case-driven build, the UC-1 churn use case + worktree plan, the wtm `ORAMA-ZETTA` blueprint as the source of truth).
- [architecture.md](architecture.md) — the node, run modes, data model, and module map.
- [schemas.md](schemas.md) — **schema as code**: the C++ embedded draft-07 schema is the single source of truth (exposed via a `*_schema()` accessor); `schemas/*.json` is a generated, drift-checked artifact (`tests/test_schemas.cpp`; regenerate with `ZETTA_WRITE_SCHEMAS=1`). How JSON-boundary schemas live and stay in sync (#464).
- [code-audit.md](code-audit.md) — a living **codebase health audit**: drift from our own conventions (inconsistencies), redundancies, code smells, and a **reconciliation against the wtm `ORAMA-ZETTA` blueprint rules** (RULE-* / PERM-* / CTL-* / TB-* / NFR-*, with a compliance verdict each). The place that says "these are the rules and how we measure against them."
- [design-system.md](design-system.md) — the **Orama design system** as it applies to the headed GUI: colour tokens, Geist typography, copy rules (sentence case, no em-dashes), the coral discipline, and the component grammar mapped to `src/gui/app.cpp`. **Read before touching the GUI.**
- [true-hybrid.md](true-hybrid.md) — **true hybrid**: one equal-peer cluster spanning heterogeneous hardware (CPU / GPU / ASIC, OS, architecture, on-prem + cloud) and the seams that make it work — `ComputeDevice` backends, the device registry, the heterogeneity-tolerant work-stealing scheduler, collectives, the equal-peer CRDT cluster, and the `Provisioner` seam — with a built-vs-planned support matrix.
- [projects.md](projects.md) — the AI project (`zetta::Project`) data model, lifecycle CRUD, and the execution graphs it owns.
- [project-inputs.md](project-inputs.md) — project inputs (`zetta::ProjectInput`): raw intent/artifact ingestion + provenance (replicated).
- [n8n-import.md](n8n-import.md) — importing an n8n workflow JSON as an artifact input (raw bytes + sha256 + schema-validated boundary).
- [n8n-compile.md](n8n-compile.md) — compiling an imported n8n workflow JSON into the ExecutionGraph IR (nodes → typed steps, connections → edges; FEAT-2 / #308).
- [parquet-metadata.md](parquet-metadata.md) — the native (no Arrow) Parquet footer / metadata parser (`zetta::parquet::parse_parquet_metadata`, ADR-32 / #505): read a file's Thrift `FileMetaData` — schema (column names/types), row groups, per-column-chunk offsets/sizes/encodings/codecs — via a self-contained Thrift compact-protocol decoder; no data decode (the layout foundation the decoders consume), non-throwing/bounds-checked, with a schema-validated JSON projection tested against a dev-time pyarrow golden (no foreign runtime in build/CI).
- [new-project-screen.md](new-project-screen.md) — the headed **New Project** screen (SCR-2): name a project, paste an NL intent, and import / drop an n8n workflow artifact — all from the GUI (FEAT-1).
- [runs.md](runs.md) — the Run (`zetta::Run`) record: status / logs / outputs / lineage, with JSON-Schema boundary validation.
- [models.md](models.md) — the Model (`zetta::Model`) entity (ENT-14 / FEAT-6): metadata replicated as `model:<uuid>`, serialized weights as a large-object body (peer-to-peer + sha256), the `system.zetta_models` registry, JSON-Schema validated.
- [compute-jobs.md](compute-jobs.md) — the ComputeJob (`zetta::ComputeJob`) record: a unit of native distributed accelerated compute (featurize/train/explain/score/ddf), lifecycle + audit + JSON-Schema boundary (ARC-11 / ENT-31).
- [dataset-partitions.md](dataset-partitions.md) — the partition catalog (`zetta::DatasetPartition`, ENT-36 / TBL-13): a replicate-to-all record of where a slice of a table's data lives (table / blob body / row range / stats / owner nodes) — the `part:<uuid>` CRDT key + reconcile + the read-only `system.dataset_partitions` computed view, JSON-Schema validated.
- [index-backend.md](index-backend.md) — the **`IndexBackend` seam** + the **`Index` entity** (ENT-39 / ENT-40, ADR-34): a pluggable build-over-partitions / query / drop interface with an `IndexRegistry` (resolve an index — or an IR `index` step — to a backend) + an in-memory reference Search backend, and a top-level replicated `Index` record `{table, kind, backend, fields}` (`index:<uuid>`, JSON-Schema validated, `system.zetta_indexes` registry). Vector / semantic backends are additive behind the same seam.
- [access-control.md](access-control.md) — key-scoped access (V1): `Principal` + `AccessKey` + `Scope` (resources) + `Capability` (rights, TTL'd), deny-by-default authorization (RULE-3 / ENT-22).
- [audit-trail.md](audit-trail.md) — the immutable, append-only `AuditEvent` (ENT-23 / FEAT-9): graph change / deploy / data-access events, replicated + JSON-Schema validated.
- [admin-panel.md](admin-panel.md) — the headed **Admin & Settings panel** (`App::draw_admin`, SCR-7 / CMP-5): read-only view of principals + keys, scope + capability grants, and the audit log.
- [jobs-panel.md](jobs-panel.md) — the headed **Compute Jobs panel** (`App::draw_jobs`, FEAT-5 / SCR): live `system.zetta_jobs` (ComputeJobs + status) + per-job objective/scaling controls previewing `ScalingPolicy::evaluate()` (set the reward, add/remove nodes). Pairs with the trained-Model + metrics + ranked drivers in the Runs panel.
- [storage.md](storage.md) — on-disk format (UUID folders, JSONL chunks) and the storage-engine seam.
- [parquet-snappy.md](parquet-snappy.md) — Parquet Snappy page decompression (`zetta::parquet::snappy_decompress`, #507): a self-contained native decoder for the Snappy raw-block form Parquet uses for its default-codec data pages, bounds-checked at the binary boundary — the first slice of the native Parquet reader (ADR-32; footer #505 / column decoders #506 / reader→DDF #508 build on it).
- [partitioner.md](partitioner.md) — the `Partitioner` seam (`zetta::Partitioner`, ADR-31 / ENT-37, #512): the pluggable, per-table policy that maps a record to a partition and a partition to its owner node(s), over a fixed partition count `P >> nodes` so rebalancing moves whole partitions (as blobs) rather than rehashing rows. Interface + the trivial `SinglePartitioner` baseline + `Table::set_partitioner`; the concrete strategies (Hash/RoundRobin #513, Rendezvous placement #514), the partition catalog (#510), and the partitioned write path (#511) are dependent slices. No new JSON boundary in this slice.
- [query.md](query.md) — the dialect-agnostic query layer and the supported Postgres subset (comparison `WHERE`, `GROUP BY` aggregation through the [DDF engine](ddf.md), and the virtual `system` tables).
- [repl-console.md](repl-console.md) — the **REPL console** component (CMP-6 / #524): the SQL / simulated-Python console behind the headed **Data → Console** view — `zetta::repl::ConsoleModel` (the engine-agnostic session model in zetta-core, CLI-reusable) + the thin `zetta::gui::ReplConsole` ImGui renderer (frontend selector, multiline editor, run/clear, scrollback transcript, result grid). Emits run events via a host-supplied handler (SQL through the query service; simulated-Python an honest "not wired yet" seam until the frontend→IR layer lands); validated headless by `tests/test_repl_console.cpp`. The governed Console/REPL screen (SCR-8, #525) hosts it next.
- [execution-graph.md](execution-graph.md) — the ExecutionGraph IR: typed step nodes/edges, the connect→clean→model→index→serve→act taxonomy, and its JSON form (`to_json`/`from_json` + schema validation).
- [intent-compiler.md](intent-compiler.md) — compiling a natural-language intent into a reviewable, editable ExecutionGraph skeleton (`zetta::compile_intent`; templated churn mapping, FEAT-2 / #311).
- [python-frontend.md](python-frontend.md) — the simulated-Python language frontend (`zetta::input::LanguageFrontend` interface + `zetta::input::PythonFrontend`, ENT-38 / ADR-33 / #520): parse a Python subset (assignments, calls, attribute/method chaining, literals) and lower it to the [ExecutionGraph IR](execution-graph.md) — calls → typed steps (via the `python_step_kind` verb table), variable refs + method receivers → data-flow edges; not a Python runtime; non-throwing; no new JSON format (output is the validated IR JSON form). The IR-targeting analogue of the query layer's `Dialect`.
- [deployments.md](deployments.md) — placing a validated execution graph onto a target (`DeploymentTarget`; R1 local), recorded + queryable.
- [deployment-controller.md](deployment-controller.md) — the control plane: reconcile a local deployment desired→actual and self-heal a killed/failed run (FEAT-4, TC-3; R1 local).
- [execution.md](execution.md) — executing an ExecutionGraph on a node (`zetta::GraphExecutor`): walk steps in dependency order, drive a Run to Succeeded/Failed.
- [churn-step-executor.md](churn-step-executor.md) — the **real** churn StepExecutor (`zetta::ChurnStepExecutor`, #396): replaces `DefaultStepExecutor`'s logical-ref placeholders with actual distributed accelerated compute behind the same seam (the orchestrator is untouched) — connect→load to DDF, clean→featurize, model→train GBDT + calibrate, index→score/rank, serve→explain (TreeSHAP), act→retention playbook, each heavy step a recorded `ComputeJob`. `run_graph` over the churn graph produces a Run whose outputs reference a real `Model` + ranked at-risk list + drivers (FEAT-5 / FEAT-6 / UC-1).
- [solution-catalog.md](solution-catalog.md) — the AI Solution Library (`zetta::SolutionCatalog`) and the headed **Deploy panel**: pick a blueprint, choose a placement on the dial, gate, and deploy (FEAT-4 / SCR-5 / CMP-3).
- [churn-solution.md](churn-solution.md) — wiring the catalog **churn-prediction** blueprint to the **real engine** (`zetta::run_churn_solution`, FEAT-4 / UC-1 / #398): encode a `ChurnDataset` to numeric DDF shards, build the standard featurize spec + GBDT params, inject a [`ChurnStepExecutor`](churn-step-executor.md), and run the blueprint — producing a real trained `Model` + ranked at-risk list + churn drivers (not the stubbed `DefaultStepExecutor`); the Deploy panel's "Run on real engine" action + the acceptance test drive it. No new JSON format.
- [cloud-inspector.md](cloud-inspector.md) — the headed **Cloud Inspector** (`zetta::CloudProviderCatalog` + `zetta::CloudInspector` + `App::draw_cloud`): inspect a deployment target (local / on-prem / Kubernetes / AWS / GCP / Azure / OCI) behind a deny-by-default, ask-every-time consent gate that names exactly what an inspect would read/call. On consent it runs the provider's read-only commands via the shared `CommandRunner`, parses each vendor's JSON at a validated boundary into identity / regions / nodes (no creds read), and surfaces it in the panel + the `system.zetta_cloud_providers` / `system.zetta_cloud_status` tables.
- [provisioner.md](provisioner.md) — the `Provisioner` seam + node capability model (`zetta::NodeCapability`): provision N nodes against a capability spec / tear down / list; cores / GPU type+throughput / memory (ARC-13 / ENT-32, #373) — plus the `LocalProvisioner` given-hardware backend (uses existing cluster nodes, best-effort; teardown is a no-op; #374).
- [aws-provisioner.md](aws-provisioner.md) — the AWS cloud-burst backend (`zetta::AwsProvisioner` + `AwsCliControlPlane`): burst N ephemeral AWS nodes (EC2 Auto Scaling Group / Spot shape via the `aws` CLI, no cloud SDK), mint bulk burst identities so they join the cluster, tear down + revoke; injectable control-plane + identity seams, schema-validated `AwsConfig` — the AWS mirror of the Azure reference, following the [cloud-provisioner pattern](cloud-provisioner-pattern.md) (ARC-13 / ADR-20, #377).
- [gcp-provisioner.md](gcp-provisioner.md) — the GCP cloud-burst `Provisioner` backend (`zetta::GcpProvisioner` + `GcpCliControlPlane`), mirroring the Azure reference via the [CLI pattern](cloud-provisioner-pattern.md): burst N nodes (Managed Instance Group / Spot shape via the `gcloud` CLI, no cloud SDK), mint bulk burst identities so they join, tear down + revoke; injectable `GcpControlPlane` + identity seams, schema-validated `GcpConfig` (ARC-13 / ADR-20, #378).
- [oci-provisioner.md](oci-provisioner.md) — the OCI cloud-burst `Provisioner` backend (`zetta::OciProvisioner` + `OciCliControlPlane`), mirroring the Azure reference via the [CLI pattern](cloud-provisioner-pattern.md): burst N nodes (Instance Pool / preemptible shape via the `oci` CLI, no cloud SDK), mint bulk burst identities so they join, tear down + revoke; injectable `OciControlPlane` + identity seams, schema-validated `OciConfig` (ARC-13 / ADR-20, #432).
- [k8s-provisioner.md](k8s-provisioner.md) — the Kubernetes cloud-burst `Provisioner` backend (`zetta::K8sProvisioner` + `K8sCliControlPlane`), mirroring the Azure reference via the [CLI pattern](cloud-provisioner-pattern.md): burst N worker pods into an existing cluster (a Deployment scaled via the `kubectl` CLI, no client lib), mint bulk burst identities so they join, tear down + revoke; injectable `K8sControlPlane` + identity seams, schema-validated `K8sConfig` (ARC-13 / ADR-20, #434).
- [bare-metal-provisioner.md](bare-metal-provisioner.md) — the bare-metal (local-host) cloud-burst `Provisioner` backend (`zetta::BareMetalProvisioner` + `BareMetalCliControlPlane`), mirroring the Azure reference via the [CLI pattern](cloud-provisioner-pattern.md): burst N local worker containers via the host runtime (`docker` / `podman`, no container SDK), mint bulk burst identities so they join, tear down + revoke; injectable `BareMetalControlPlane` + identity seams, schema-validated `BareMetalConfig`. Complements `LocalProvisioner` (which *reports* nodes; this *bursts* them) (ARC-13 / ADR-20, #436).
- [burst-identity.md](burst-identity.md) — bulk-mint a short-lived service `Principal` + `AccessKey` per burst node on provision and bulk-revoke on teardown (`zetta::BurstIdentityManager`), reusing the identity model, audited (ARC-13 / RSK-9, #375).
- [scaling-policy.md](scaling-policy.md) — the job objective / reward model (`zetta::ScalingPolicy`): a per-job autoscaler objective (minimize cost / runtime-latency target / data shape) with bounds (min/max nodes, cost cap) + objective evaluation over (progress, elapsed, cost) samples (ADR-29 / ENT-34, #370).
- [burst-approval-gate.md](burst-approval-gate.md) — the large-burst cost-cap approval gate (`zetta::BurstApprovalGate`): a `Provisioner` decorator that blocks an over-cap provision burst pending approval and records the decision in the audit trail (APR-3 / RSK-9, #379).
- [job-autoscaler.md](job-autoscaler.md) — the autoscaler control loop (`zetta::JobAutoscaler`): each tick observe a running `ComputeJob`'s progress, score it with the job's `ScalingPolicy`, and add/remove nodes through the `Provisioner` seam within bounds, with hysteresis (anti-thrash); reads live membership each tick (elastic) and degrades to best-effort max utilization on given hardware; schema-validated `AutoscalerConfig` (ADR-29 / ARC-11, #371).
- [add-nodes.md](add-nodes.md) — the **permanent-add control entry point** (`zetta::add_nodes`, #518): the "add 10 nodes to this cluster" action over the `Provisioner` seam — drive a provisioner (the cloud-burst `AzureProvisioner`, or any backend) to bring up N nodes that auto-join via the seed-peer handshake and persist as ordinary `node:<id>` members. The *permanent* sibling of the autoscaler: it only provisions and reports, **never** tearing a member down or revoking — elastic / cost-cap burst is deferred. Vendor-neutral; schema-validated `AddNodesRequest` control-command boundary.
- [azure-provisioner.md](azure-provisioner.md) — the reference cloud-burst backend (`zetta::AzureProvisioner` + `AzCliControlPlane`): burst N ephemeral Azure nodes (VMSS / Spot shape via the `az` CLI, no cloud SDK), mint bulk burst identities so they join the cluster, tear down + revoke; injectable control-plane + identity seams, schema-validated `AzureConfig` (ARC-13 / ADR-20, #376; AWS #377 / GCP #378 mirror it).
- [cloud-provisioner-pattern.md](cloud-provisioner-pattern.md) — the recipe every cloud-burst backend follows (the shape `AzureProvisioner` set, GCP / OCI / Kubernetes / bare-metal / AWS mirror): the four pieces (`<Vendor>Provisioner` / `<Vendor>ControlPlane` / `<Vendor>CliControlPlane` / `<Vendor>Config`), the shared `CommandRunner` + identity hooks, the lifecycle→CLI mapping (VMSS ↔ ASG ↔ MIG ↔ Instance Pool ↔ Deployment ↔ local containers), and the step-by-step. **CLI for now.**
- [large-objects.md](large-objects.md) — storing files as large objects and importing JSON/JSONL records.
- [compute-device.md](compute-device.md) — the `zetta::compute::ComputeDevice` operator interface + typed device-buffer / memory model + the host-memory stub (ADR-27 / ARC-9, accelerated compute; #359), plus the `zetta-compute` build target + the optional CUDA backend (`CudaDevice`; #363).
- [cpu-device.md](cpu-device.md) — the `zetta::compute::CpuDevice` reference backend: every operator on host memory, multi-threaded via `runtime::parallel_for` (ADR-27 / ARC-9; #360).
- [device-registry.md](device-registry.md) — the per-node device registry (`zetta::compute::DeviceRegistry`): enumerate a node's compute devices, report each one's capability, and select a backend per op (CPU-first / GPU-when-present) (ARC-9, #362).
- [ddf.md](ddf.md) — the DDF DataFrame core (`zetta::ddf::DataFrame`): a typed, columnar, chunked frame over the storage engine, each chunk backed by a `ComputeDevice` buffer — the substrate DDF ops operate on (ARC-12 / GLO-11 / ENT-33; #380).
- [ddf-ops.md](ddf-ops.md) — the local DDF DataFrame ops: `zetta::ddf::scan` / `filter` / `project` (read a table into a frame, `gather`-based row filtering, `map`/`elementwise` computed columns, with schema-validated `FilterPredicate` / `Projection` boundaries; #381) and `zetta::ddf::sort` / `concat` / `slice` (key-column sort via the device `sort_by_key`, row-wise union, contiguous row range — the single-node building blocks of the distributed sort; #385) (ARC-12).
- [ddf-distributed-sort.md](ddf-distributed-sort.md) — the DDF distributed sort (`zetta::ddf::DistributedSorter`): sample-partition + local sort + merge across the cluster — gather-sampled splitters over the collectives, an all-to-all row shuffle over the signal plane (schema-validated `PartitionMessage`), returning globally range-ordered, locally-sorted partitions (ARC-12; #385).
- [ddf-join.md](ddf-join.md) — the DDF distributed equi-join (`zetta::ddf::distributed_join`): repartition two frames by key via collectives (gather + broadcast), then a local hash / sort-merge join per shard — single-node and multi-node yield identical results (ARC-12; #382).
- [ddf-groupby.md](ddf-groupby.md) — the DDF distributed groupby-aggregate (`zetta::ddf::group_by` / `distributed_group_by`): groupby + count/sum/min/max/mean over a frame's columns, partial-per-node combined via gather/merge/broadcast for results identical single- and multi-node (ARC-12; #383) — and runnable as a recorded `ddf` `ComputeJob` (`run_group_by_job`) through the job coordinator, so it appears in `system.zetta_jobs` (FEAT-8; #387).
- [ddf-as-of.md](ddf-as-of.md) — the DDF window / as-of (point-in-time) op (`zetta::ddf::as_of_aggregate`): for each entity, reduce only the rows at or before an `as_of` cutoff (optionally also after a `window_start` lower bound) — the leakage-free featurization primitive over the DDF substrate (ARC-12; #384).
- [ddf-featurize.md](ddf-featurize.md) — point-in-time featurization (`zetta::ddf::point_in_time_featurize` + `run_featurize_job`): express the churn `churn_features.sql` shape as a DDF graph (join + groupby-aggregate + as-of window) → a leakage-free feature table for training (every feature uses `time <= as_of`); distributed as a recorded `featurize` ComputeJob (ARC-12 / FEAT-6; #388).
- [gbdt.md](gbdt.md) — distributed histogram GBDT training (`zetta::ml::train_gbdt` + `run_train_job`): histogram gradient-boosted decision trees with a binary-logistic objective — per-feature gradient/Hessian histograms over bins, allreduced across nodes each round to find splits (single-node == multi-node); a host-side reference over device-backed feature columns; runs as a recorded `train` ComputeJob and **produces a `Model`** (schema-validated weights + metrics + ranked drivers), trained on the churn fixture to a target AUC (FEAT-6 / ENT-14; #390).
- [gbdt-score.md](gbdt-score.md) — batch scoring / rank-at-risk over a trained `Model` (`zetta::ml::score_gbdt` + `run_score_job`): score entities to a **calibrated churn risk** (the binary-logistic `predict_proba`) and rank them into an **at-risk list**; the distributed `score` ComputeJob is SPMD (per-shard predict, gather + device `sort_by_key` rank + broadcast → identical ranking single-node == multi-node), with `load_gbdt_model` re-validating the weights body at the GBDT model JSON Schema boundary; the inference counterpart to the trainer, GPU-native / CPU-fallback / distributed (FEAT-6 / CMD-10; #392).
- [calibration.md](calibration.md) — probability calibration (`zetta::ml::Calibrator` + `fit_calibrator` + `calibrate_model`): Platt scaling + isotonic regression fit on a held-out split so the GBDT's risk scores are well-calibrated (Brier / ECE improve, AUC preserved); attaches to a `GbdtModel` (predict_proba applies it) and wires into the distributed `train` job via a content-hash held-out split (single-node == multi-node), schema-validated boundary (FEAT-6; #391).
- [tree-shap.md](tree-shap.md) — exact TreeSHAP explanation (`zetta::ml::tree_shap` + `run_explain_job`): exact path-dependent TreeSHAP over the trained GBDT trees (Lundberg 2018, Algorithm 2) using the per-node cover the trainer records on each `TreeNode` — per-entity per-feature attributions in raw/margin space (efficiency `base + Σ φ = predict_raw`), a per-entity dominant churn driver, and a distributed `explain` ComputeJob with an allreduced global mean-|φ| driver ranking (single-node == multi-node) (FEAT-6; #393).
- [native-oracle.md](native-oracle.md) — the native correctness oracle (`zetta::ml::load_golden_oracle` + `tests/test_native_oracle.cpp`, RSK-8 / #395): prove the native featurize / GBDT-train / TreeSHAP reimplementations are correct **without running any reference** (no Python/XGBoost/foreign runtime) via three self-contained C++ layers over the churn fixture — committed **golden numeric fixtures** (cross-checked against a leakage-free ground truth + the SHAP efficiency identity), **analytic** closed-form GBDT-split + TreeSHAP micro-tests, and single-node == 2-node == 3-node **equivalence**; the golden is a schema-validated boundary, regenerated offline via `ZETTA_WRITE_GOLDEN=1`.
- [playbook.md](playbook.md) — the UC-1 retention playbook (`zetta::ml::generate_playbook`): turn the model's [calibrated risk](gbdt-score.md) + [dominant churn driver](tree-shap.md) into a CRM-ready playbook — a deterministic driver→action→owner dictionary (`PlaybookPolicy`), expected-retained-value priority (`P(churn) × ARR × P(save|driver)`, frozen in code), and a constrained narrator behind a seam (default Claude; writes the narrative + picks the play within a strict JSON schema, never invents numbers) with a deterministic rules-engine fallback so it always runs offline; plus an outcome log for the feedback loop (FEAT-6; #397).
- [uc1-end-to-end.md](uc1-end-to-end.md) — the **UC-1 end-to-end** integration test (`tests/test_uc1_end_to_end.cpp`, #399; realizes UC-1 / satisfies TP-1): drives the whole churn pipeline on the [synthetic fixture](churn-dataset.md) in one test — synthetic data → [featurize](ddf-featurize.md) (point-in-time, [entity-resolved](entity-resolution.md)) → [train GBDT](gbdt.md) → [explain (TreeSHAP)](tree-shap.md) → ranked at-risk + drivers → playbook, behind the real [`ChurnStepExecutor`](churn-step-executor.md) — and asserts a **calibrated ranked list** + **division-correct resolution** + a **gated** ([correctness gate](gate.md) / [entity-resolution check](entity-resolution-check.md), RULE-1), **governed** ([key-scoped access](access-control.md) + [audit trail](audit-trail.md)) run; a conflating resolver is shown to block the gate.
- [test-suite.md](test-suite.md) — the in-app **test suite** (`zetta::testkit` + the headed **Operations → Test suite** panel, #462): a headless-runnable catalog of canned, parameterized cases over the real engine — compute / device operators, DDF ops, ML (GBDT / TreeSHAP / calibration), distributed / cluster over a **real multi-node loopback cluster**, governance, and the whole [UC-1 pipeline](uc1-end-to-end.md) — each with a per-test options modal + custom-data support; the catalog lives in zetta-core (GUI is a thin renderer), validated headless by `tests/test_testkit.cpp`. Includes an **"adding a case"** how-to and an **inventory of candidate cases** (the backlog of engine surfaces that could become runnable cases, by category, with effort/infra markers).
- [example-scripts.md](example-scripts.md) — the **sim-Python example-script harness** (`zetta::testkit::run_example_script` + `example_scripts()`, #523): run a sim-Python example program end to end as an integration test — **parse** ([python-frontend](python-frontend.md)) → **IR** → **gate** ([gate](gate.md), RULE-1) → **run** ([execution](execution.md)) — and assert on the outputs (shape, step kinds, edges, produced `dataset`/`model`/`index` outputs), so *the example programs ARE the integration tests*. A green script doubles as a usage example; a negative one proves a failure surfaces the **offending statement** (the parser's locator, or the failing step reconstructed from its `python` provenance). Each is a `TestCase` under the new **`TestCategory::Examples`**, run headless (`tests/test_example_scripts.cpp`) and in the Test suite panel; non-throwing; no new JSON format. TC-9/10/11/13 + UC-1-at-scale land as their bindings (#522, parquet→DDF, partitioning, fulltext) do.
- [work-stealing-scheduler.md](work-stealing-scheduler.md) — the work-stealing scheduler (`zetta::compute::WorkStealingScheduler` local + `DistributedScheduler` cross-node): a job split into tasks, idle/faster workers/nodes steal pending work, with elastic mid-job membership — join/leave/lost-node re-exec (ARC-10; #366 / #367).
- [job-coordinator.md](job-coordinator.md) — the job coordinator (`zetta::compute::JobCoordinator`): the single entry the compute algorithms (DDF/GBDT/SHAP) submit work through — splits a `ComputeJob` into tasks on the work-stealing scheduler, drives collectives at round boundaries (SPMD), and drives the job lifecycle (ARC-11; #372).
