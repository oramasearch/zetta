# zetta docs

zetta is a database. A *zetta node* is one running instance; it runs **headed**
(default — with an SDL3 + Dear ImGui UI) or **headless** (no UI, for servers).
This directory documents the system; keep it in sync as the system changes.

- [orama-zetta.md](orama-zetta.md) — **read first**: what Orama Zetta is and the working product decisions (naming, value-first messaging, AI projects as the central item, the use-case-driven build, the UC-1 churn use case + worktree plan, the wtm `ORAMA-ZETTA` blueprint as the source of truth).
- [architecture.md](architecture.md) — the node, run modes, data model, and module map.
- [schemas.md](schemas.md) — **schema as code**: the C++ embedded draft-07 schema is the single source of truth (exposed via a `*_schema()` accessor); `schemas/*.json` is a generated, drift-checked artifact (`tests/test_schemas.cpp`; regenerate with `ZETTA_WRITE_SCHEMAS=1`). How JSON-boundary schemas live and stay in sync (#464).
- [code-audit.md](code-audit.md) — a living **codebase health audit**: drift from our own conventions (inconsistencies), redundancies, code smells, and a **reconciliation against the wtm `ORAMA-ZETTA` blueprint rules** (RULE-* / PERM-* / CTL-* / TB-* / NFR-*, with a compliance verdict each). The place that says "these are the rules and how we measure against them."
- [design-system.md](design-system.md) — the **Orama design system** as it applies to the headed GUI: colour tokens, Geist typography, copy rules (sentence case, no em-dashes), the coral discipline, and the component grammar mapped to `src/gui/app.cpp`. **Read before touching the GUI.**
- [true-hybrid.md](true-hybrid.md) — **true hybrid**: one equal-peer cluster spanning heterogeneous hardware (CPU / GPU / ASIC, OS, architecture, on-prem + cloud) and the seams that make it work — `ComputeDevice` backends, the device registry, the heterogeneity-tolerant work-stealing scheduler, collectives, the equal-peer CRDT cluster, and the `Provisioner` seam — with a built-vs-planned support matrix.
- [projects.md](projects.md) — the AI project (`zetta::Project`) data model, lifecycle CRUD, and the execution graphs it owns.
- [project-inputs.md](project-inputs.md) — project inputs (`zetta::ProjectInput`): raw intent/artifact ingestion + provenance (replicated).
- [n8n-import.md](n8n-import.md) — importing an n8n workflow JSON as an artifact input (raw bytes + sha256 + schema-validated boundary).
- [n8n-compile.md](n8n-compile.md) — compiling an imported n8n workflow JSON into the ExecutionGraph IR (nodes → typed steps, connections → edges; FEAT-2 / #308).
- [parquet-metadata.md](parquet-metadata.md) — the native (no Arrow) Parquet footer / metadata parser (`zetta::parquet::parse_parquet_metadata`, ADR-32 / #505): read a file's Thrift `FileMetaData` — schema (column names/types), row groups, per-column-chunk offsets/sizes/encodings/codecs — via a self-contained Thrift compact-protocol decoder; no data decode (the layout foundation the decoders consume), non-throwing/bounds-checked, with a schema-validated JSON projection tested against a dev-time pyarrow golden (no foreign runtime in build/CI).
- [new-project-screen.md](new-project-screen.md) — the headed **New Project** screen (SCR-2): name a project, paste an NL intent, and import / drop an n8n workflow artifact — all from the GUI (FEAT-1).
- [runs.md](runs.md) — the Run (`zetta::Run`) record: status / logs / outputs / lineage, with JSON-Schema boundary validation.
- [models.md](models.md) — the Model (`zetta::Model`) entity (ENT-14 / FEAT-6): metadata replicated as `model:<uuid>`, serialized weights as a large-object body (peer-to-peer + sha256), the `system.zetta_models` registry, JSON-Schema validated.
- [compute-jobs.md](compute-jobs.md) — the ComputeJob (`zetta::ComputeJob`) record: a unit of native distributed accelerated compute (featurize/train/explain/score/ddf), lifecycle + audit + JSON-Schema boundary (ARC-11 / ENT-31).
- [dataset-partitions.md](dataset-partitions.md) — the partition catalog (`zetta::DatasetPartition`, ENT-36 / TBL-13): a replicate-to-all record of where a slice of a table's data lives (table / blob body / row range / stats / owner nodes) — the `part:<uuid>` CRDT key + reconcile + the read-only `system.dataset_partitions` computed view, JSON-Schema validated.
- [system-datasets.md](system-datasets.md) — datasets as a first-class observability primitive (`zetta::Node::datasets()` + the read-only **`system.datasets`** view, #585; the engine source for the area-3 dataset view in epic #575). One row per dataset (= a table + its data) aggregating schema / rows / on-disk size / storage format / [replication strategy](replication-strategy.md) + **partition placement across the cluster** (which node owns which partition, joined from the replicate-to-all [partition catalog](dataset-partitions.md)). No stored entity — computed at query time from the live tree + catalog, so it never drifts; `Node::datasets()` is the single source the SQL view and the [GUI Datasets panel](datasets-panel.md) both read. Adds no new JSON boundary.
- [datasets-panel.md](datasets-panel.md) — the headed **Datasets view** (`App::draw_datasets` + `App::draw_dataset_placement`, **Data → Datasets**; #586, area 3 of epic #575): the GUI form of [`system.datasets`](system-datasets.md) — a **thin renderer** list + detail showing the selected dataset's schema / rows / on-disk size / format / [replication strategy](replication-strategy.md), plus **partition placement across the cluster** as a node-box overlay (reusing the [Cluster view](cluster.md)'s spatial grammar — owners highlighted, non-owners dimmed, departed/foreign owners still shown) over a per-partition `[start,end) → owners` table. Recomputed from `Node::datasets()` + `Cluster::nodes()` each frame; no GUI-only state, no new JSON boundary.
- [add-dataset.md](add-dataset.md) — the **"Add dataset" affordance** (`zetta::add_dataset_file`, `include/zetta/add_dataset.hpp`; #587, area 3 of epic #575): load a local `parquet`/`jsonl`/`json`/`csv` file as a **partitioned table** so it surfaces in the [Datasets view](datasets-panel.md) / [`system.datasets`](system-datasets.md) with its partitions placed across the cluster. The reusable zetta-core engine backend (decode by extension via the native [Parquet reader](parquet-reader.md) / JSON / CSV → free-form rows, then [`write_partitioned`](partitioned-write-path.md) with a [`RendezvousPlacement`](partitioner.md) partitioner so slices land on specific owner nodes), plus the headed affordance (a **Datasets-view button**, **drag-drop onto the view**, and a **File → Add dataset…** item) that calls it on the UI thread. The GUI, all-formats, file-picker counterpart to the sim-Python [`datasets` shim](datasets-shim.md) (#521); CSV cells are type-inferred (leading-zero-safe), no new JSON boundary (rows are schemaless, placement rides the validated [`DatasetPartition`](dataset-partitions.md) catalog).
- [sharded-blob-placement.md](sharded-blob-placement.md) — partition-aware large-object body replication (`zetta::ReplicatedBlobStore`, #515): a `Partitioned` / `PartitionedWithReplicas` table's partition body (`blob_ref`) is fetched + held **only by its owner node(s)** per the [partition catalog](dataset-partitions.md)'s `owner_nodes` + replication factor (`rf` owners → exactly `rf` copies), instead of replicate-to-all — `missing_blobs()` skips a non-owner's partition body and `store_blob()` refuses it; plain large objects + model weights are unaffected. The first slice that *acts* on a non-default [replication strategy](replication-strategy.md) at the body level.
- [index-backend.md](index-backend.md) — the **`IndexBackend` seam** + the **`Index` entity** (ENT-39 / ENT-40, ADR-34): a pluggable build-over-partitions / query / drop interface with an `IndexRegistry` (resolve an index — or an IR `index` step — to a backend) + an in-memory reference Search backend, and a top-level replicated `Index` record `{table, kind, backend, fields}` (`index:<uuid>`, JSON-Schema validated, `system.zetta_indexes` registry). Vector / semantic backends are additive behind the same seam.
- [oramacore-fulltext-index.md](oramacore-fulltext-index.md) — the **`OramaCoreFulltextIndex`** backend (ENT-39 / ENT-40, ADR-34, #527): the **first real `IndexBackend`** — a **full-text (BM25F)** Search backend (name `oramacore_fulltext`) over the native **oramacore-cpp** engine (the vendored C++23 OramaCore full-text port). `build` indexes each row's field text; `query` reads `term` as a free-text query and returns row ids **ranked** by relevance. The engine is held behind a pImpl + linked PRIVATE, and the whole integration is **guarded on the (private) submodule's presence** (`ZETTA_WITH_ORAMACORE`) so a CPU-only checkout still builds/runs green (the backend degrades to `Unsupported`). No new JSON boundary.
- [index-step-executor.md](index-step-executor.md) — the **run-path wiring** for an `index` step (`zetta::IndexStepExecutor` + `Node::index_registry()`, #528): the `Node` now owns an `IndexRegistry` (the reference backends registered — `memory_search` always, `oramacore_fulltext` when built), and the [`StepExecutor`](execution.md) resolves a deployed `index` step to its backend ([`index_spec_from_node`](index-backend.md)), reads the source table's rows into partitions, **builds a real index**, records the [`Index`](index-backend.md) entity, and leaves it **queryable** (`node.index_registry().resolve(spec)->query(...)`) — the acceptance "an index step builds a real index that is then queryable". Other step kinds delegate to `DefaultStepExecutor`; churn's `index` step now builds a real entity index too (alongside the at-risk ranking). No new JSON format.
- [distributed-fulltext.md](distributed-fulltext.md) — **per-partition distributed full-text** (`zetta::DistributedFulltextIndex`, ENT-39 / ENT-40, ADR-34, #529 — the engine half of TC-13 #503): the approved per-partition topology — each node builds a full-text sub-index over the partitions it OWNS (compute-near-data), and a query is answered by **scatter-gather + merge/rank** across those sub-indexes (over the `fulltext.query` signal-plane RPC, schema-validated), not one consolidated index. The distributed ranking **matches a single consolidated-index oracle** (the standard sharded-search local-IDF query-then-fetch shape; exact for the global top-k when ranking is tf-unambiguous). The seam now carries per-hit `scores`; the merge + scatter-gather are tested engine-agnostically (a partition-independent reference scorer) with the real BM25F path skipped when the [oramacore](oramacore-fulltext-index.md) submodule is absent. The **TC-13 ([#503](https://github.com/oramasearch/zetta/issues/503)) acceptance** is also a GUI-runnable [test-suite](test-suite.md) case, `cluster.fulltext_index` — build over each node's owned partitions, scatter-gather query, ranking == the consolidated oracle on every node.
- [access-control.md](access-control.md) — key-scoped access (V1): `Principal` + `AccessKey` + `Scope` (resources) + `Capability` (rights, TTL'd), deny-by-default authorization (RULE-3 / ENT-22).
- [audit-trail.md](audit-trail.md) — the immutable, append-only `AuditEvent` (ENT-23 / FEAT-9): graph change / deploy / data-access events, replicated + JSON-Schema validated.
- [admin-panel.md](admin-panel.md) — the headed **Admin & Settings panel** (`App::draw_admin`, SCR-7 / CMP-5): read-only view of principals + keys, scope + capability grants, and the audit log.
- [jobs-panel.md](jobs-panel.md) — the headed **Compute Jobs panel** (`App::draw_jobs`, FEAT-5 / SCR): live `system.zetta_jobs` (ComputeJobs + status) + per-job objective/scaling controls previewing `ScalingPolicy::evaluate()` (set the reward, add/remove nodes). Pairs with the trained-Model + metrics + ranked drivers in the Runs panel.
- [models-panel.md](models-panel.md) — the headed standalone **Models view** (`App::draw_models`, part of #575): the GUI form of `system.zetta_models` — list + detail (metrics, ranked drivers, weights fingerprint, reusing the Runs panel's `render_model_card`) + an inline **Add model** affordance (register/import via `create_model` + optional `set_weights`, re-validated against the Model JSON Schema at the form boundary).
- [storage.md](storage.md) — on-disk format (UUID folders, JSONL chunks) and the storage-engine seam.
- [parquet-snappy.md](parquet-snappy.md) — Parquet Snappy page decompression (`zetta::parquet::snappy_decompress`, #507): a self-contained native decoder for the Snappy raw-block form Parquet uses for its default-codec data pages, bounds-checked at the binary boundary — the first slice of the native Parquet reader (ADR-32; footer #505 / column decoders #506 / reader→DDF #508 build on it).
- [parquet-column-decoders.md](parquet-column-decoders.md) — the native (no Arrow) Parquet column-chunk decoders (`zetta::parquet::decode_column` / `decode_column_chunk`, ADR-32 / #506): read a column's data pages into typed values + a validity bitmap on top of the [footer parser](parquet-metadata.md) + [Snappy codec](parquet-snappy.md) — PLAIN (int/float/bool/byte_array) + dictionary (RLE/bit-packed indices), definition levels for the (mostly non-null) columns, uncompressed + snappy codecs (zstd/gzip rejected with a reason); non-throwing/bounds-checked, schema-validated JSON projection tested against a dev-time pyarrow golden. Projecting these into [DDF](ddf.md) columns is the [reader → DDF slice](parquet-reader.md) (#508).
- [parquet-reader.md](parquet-reader.md) — the native (no Arrow) Parquet **reader → DDF columns with column projection** (`zetta::ddf::load_parquet_data_frame` + `zetta::parquet::read_parquet_rows`, ADR-32 / #508): the capstone that assembles the [footer parser](parquet-metadata.md) (#505) + [column decoders](parquet-column-decoders.md) (#506) + [Snappy codec](parquet-snappy.md) (#507) into a reader that materializes a **requested subset** of columns straight into a typed, chunked [DDF `DataFrame`](ddf.md) (DeviceBuffers) — column projection reads only the selected column chunks, so it loads engineered numeric columns + a label while **dropping `embedding_0..3071`**. Removes the `ChurnDataFormat::Parquet` "not yet supported" error and wires Parquet into the [churn loader](churn-dataset.md) via the untyped rows reader; numeric/dense boundary (nulls / byte_array / real-into-int rejected), schema-validated golden, TC-9 (#499) parity vs a dev-time pyarrow golden (no foreign runtime in build/CI).
- [partitioner.md](partitioner.md) — the `Partitioner` seam (`zetta::Partitioner`, ADR-31 / ENT-37, #512): the pluggable, per-table policy that maps a record to a partition and a partition to its owner node(s), over a fixed partition count `P >> nodes` so rebalancing moves whole partitions (as blobs) rather than rehashing rows. The seam + the trivial `SinglePartitioner` baseline + `Table::set_partitioner` (#512); the two **record→partition** strategies (#513): `HashPartitioner` (`hash(key columns) % P`, deterministic shard-by-key via a stable FNV-1a, balanced for a typical key) and `RoundRobinPartitioner` (`surrogate % P`, even balance regardless of key skew), with the `partitioner_from_json`/`to_json` JSON config boundary (`schemas/partitioner.schema.json`, the hand-written value-type pattern); and the **partition→node** strategy `RendezvousPlacement` (`zetta::RendezvousPlacement`/`rendezvous_owners`, #514) — rendezvous / highest-random-weight (HRW) placement, so adding/removing one node reassigns only ~1/N of partitions, deterministic + leaderless. The partition catalog (#510) and the partitioned write path (#511) — which composes assignment + placement and owns the universal polymorphic config boundary — are dependent slices.
- [partitioned-write-path.md](partitioned-write-path.md) — the **partitioned write path** (`zetta::write_partitioned`, #511): rows → partition → blob, placement recorded. For a table with a [`Partitioner`](partitioner.md) it assigns each row to a partition (stamping the round-robin surrogate), serializes each non-empty partition's rows to a JSON Lines blob, stores it as a [large object](large-objects.md) (`LargeObjectStore::import_bytes`, so the body gossips peer-to-peer + is sha256-verified), and records a [`DatasetPartition`](dataset-partitions.md) catalog entry per partition (blob ref + cumulative row range + `place_partition` owners), visible in `system.dataset_partitions`. Composes #510/#512–#514; no new JSON schema (the catalog entry is the existing boundary, the blob is an LO body).
- [partition-rebalance.md](partition-rebalance.md) — **between-jobs rebalance on a membership change** (`zetta::rebalance_partitions`, #517; satisfies TC-10/#500): when a node joins, recompute [rendezvous (HRW)](partitioner.md) placement for the sharded partitions and update each changed [`DatasetPartition`](dataset-partitions.md)'s `owner_nodes` (via the capturing `set_owner_nodes` mutator), so ≈rf/N partitions move onto the new node and the bodies follow over the [sharded-blob-placement](sharded-blob-placement.md) (#515) seam — every row still readable exactly once with rf owners. `rf` is preserved from the catalog's current owner count; replicate-to-all partitions are left untouched. Auto-triggered inside `Node::tick()` off the replicated `node:<id>` membership keys (no `Cluster` plumbing). No new JSON format. Out of scope: locality reads (#516), physical body GC, mid-job/elastic rebalance.
- [query.md](query.md) — the dialect-agnostic query layer and the supported Postgres subset (comparison `WHERE`, `GROUP BY` aggregation through the [DDF engine](ddf.md), and the virtual `system` tables).
- [node-metrics.md](node-metrics.md) — **live per-node resource telemetry** (`zetta::NodeMetricsSampler` / `system.node_metrics`, #575 area 2): each node samples its own host's OS counters (CPU / memory / GPU + VRAM / storage / network) at query time and emits one utilization row — an **ephemeral, observed** read view with **no CRDT backing** (like `system.zetta_cloud_status`). The engine source for the animated per-node gauges; in `zetta-core` (no SDL, headless-testable). Counters a host can't report degrade gracefully to `null` (GPU absent in a CPU-only core build).
- [pipeline-instrumentation.md](pipeline-instrumentation.md) — **live pipeline instrumentation as observable read views** (`system.pipeline_jobs` / `system.collective_rounds`, #589 / #575 area 5 — the engine source the GUI's algorithm-at-work animation reads from): the live distributed-compute pipeline's instrumentation — the per-job **near-data** counters (`local_bytes_read` vs `wire_bytes_moved`, recorded into a bounded in-memory ring on the node by the near-data runners) and the live **collective-plane** progress (the running [job coordinator](job-coordinator.md)'s `rounds_completed` + cumulative `wire_bytes`) — surfaced as two read-only `system.<table>` views so the GUI reads from SQL, not bespoke hooks. **Ephemeral, observed, NOT replicated** (no CRDT, no new JSON boundary) like [`system.node_metrics`](node-metrics.md) / [`system.checkpoints`](job-checkpoint.md); in `zetta-core` (no SDL, headless-testable). The placement timeline is the existing [`system.dataset_partitions`](dataset-partitions.md) (ordered by `created`).
- [cluster-node-gauges.md](cluster-node-gauges.md) — **animated per-node resource gauges + sparklines** on the headed cluster node boxes (#584, #575 area 2): live CPU / memory / GPU + VRAM / storage / network as eased moving bars + sparklines (Orama semantic green/amber/red, graceful n/a), fed by a **cluster-wide telemetry exchange over the [signal plane](signal-plane.md)** (`zetta::NodeTelemetryExchange`) — each node broadcasts its own [`system.node_metrics`](node-metrics.md) as an ephemeral `node.metrics` event and every node caches its peers', so `Node::telemetry_snapshot()` returns the whole cluster's gauges (self + fresh peers). Not replicated (a measurement, not durable state); the wire payload is schema-validated (`node_metrics_wire_schema()`). A thin GUI renderer over the snapshot.
- [repl-console.md](repl-console.md) — the **REPL console** component (CMP-6 / #524): the SQL / simulated-Python console behind the headed **Data → Console** view — `zetta::repl::ConsoleModel` (the engine-agnostic session model in zetta-core, CLI-reusable) + the thin `zetta::gui::ReplConsole` ImGui renderer (frontend selector, multiline editor, run/clear, scrollback transcript, result grid). Emits run events via a host-supplied handler; validated headless by `tests/test_repl_console.cpp`. The governed Console/REPL screen (SCR-8, #525) hosts it — see below.
- [governed-console.md](governed-console.md) — the **governed Console/REPL screen** (SCR-8 / #525): the headed screen hosting the [REPL console](repl-console.md), with a governed run handler (`zetta::repl::GovernedConsole`, zetta-core) so every statement is **capability-scoped** against the acting key, simulated-Python **lowers to the IR + passes the [correctness gate](gate.md)** before it runs, and **each statement is recorded in the [audit trail](audit-trail.md)** as a `data_access` event (FEAT-9). Realizes UC-3 (ad-hoc question, governed). Tabular results for both frontends; a "Run as" selector chooses the key; no new JSON boundary.
- [execution-graph.md](execution-graph.md) — the ExecutionGraph IR: typed step nodes/edges, the connect→clean→model→index→serve→act taxonomy, and its JSON form (`to_json`/`from_json` + schema validation).
- [graph-plan.md](graph-plan.md) — the **graph-over-cluster plan view** (`zetta::project_cluster_plan` + the Graph Workspace's `App::draw_graph_plan`, #591, part of #575 area 6): project how an [ExecutionGraph](execution-graph.md) would run over the **current** cluster — which steps run **near their data**, which **fan out** SPMD, the **owner nodes** each lands on — over the IR + the [partition catalog](dataset-partitions.md) + the live [`Cluster::nodes()`](cluster.md). A pure, tested zetta-core projection (connect → near-data/all-nodes; clean/model/index/serve → near-data/fan-out; act → coordinator; near-data locality propagated forward along DataFlow edges), rendered as a canvas overlay + cluster strip + per-step placement table. A **projection** of zetta's SPMD + compute-near-data model, not a committed schedule (no per-step scheduler yet); thin renderer, no new JSON boundary.
- [intent-compiler.md](intent-compiler.md) — compiling a natural-language intent into a reviewable, editable ExecutionGraph skeleton (`zetta::compile_intent`; templated churn mapping, FEAT-2 / #311).
- [python-frontend.md](python-frontend.md) — the simulated-Python language frontend (`zetta::input::LanguageFrontend` interface + `zetta::input::PythonFrontend`, ENT-38 / ADR-33 / #520): parse a Python subset (assignments, calls, attribute/method chaining, literals) and lower it to the [ExecutionGraph IR](execution-graph.md) — calls → typed steps (via the `python_step_kind` verb table), variable refs + method receivers → data-flow edges; not a Python runtime; non-throwing; no new JSON format (output is the validated IR JSON form). The IR-targeting analogue of the query layer's `Dialect`.
- [datasets-shim.md](datasets-shim.md) — the simulated HuggingFace `datasets` shim (`zetta::input::run_load_dataset_step` + `DatasetStepExecutor`, #521): a sim-Python `load_dataset("<path>", columns=[...])` lowers to an IR connect/load step (parquet path + column projection), and the binding decodes the referenced Parquet bytes with the native [Parquet reader](parquet-reader.md) (no Arrow / HF runtime / network — those are fidelity references only) into a (optionally [partitioned](partitioned-write-path.md)) table; file/network IO behind the injectable `DatasetResolver` seam (offline default = local path); no new JSON format.

- [execution.md](execution.md) — executing an ExecutionGraph on a node (`zetta::GraphExecutor`): walk steps in dependency order, drive a Run to Succeeded/Failed.
- [churn-step-executor.md](churn-step-executor.md) — the **real** churn StepExecutor (`zetta::ChurnStepExecutor`, #396): replaces `DefaultStepExecutor`'s logical-ref placeholders with actual distributed accelerated compute behind the same seam (the orchestrator is untouched) — connect→load to DDF, clean→featurize, model→train GBDT + calibrate, index→score/rank, serve→explain (TreeSHAP), act→retention playbook, each heavy step a recorded `ComputeJob`. `run_graph` over the churn graph produces a Run whose outputs reference a real `Model` + ranked at-risk list + drivers (FEAT-5 / FEAT-6 / UC-1).
- [solution-catalog.md](solution-catalog.md) — the AI Solution Library (`zetta::SolutionCatalog`) and the headed **Deploy panel**: pick a blueprint, choose a placement on the dial, gate, and deploy (FEAT-4 / SCR-5 / CMP-3).
- [churn-solution.md](churn-solution.md) — wiring the catalog **churn-prediction** blueprint to the **real engine** (`zetta::run_churn_solution`, FEAT-4 / UC-1 / #398): encode a `ChurnDataset` to numeric DDF shards, build the standard featurize spec + GBDT params, inject a [`ChurnStepExecutor`](churn-step-executor.md), and run the blueprint — producing a real trained `Model` + ranked at-risk list + churn drivers (not the stubbed `DefaultStepExecutor`). **Interactive runs go over the live cluster** (`run_churn_solution_on_node` + `is_churn_graph`, #580): the run executes on the node's **live** `JobCoordinator` (the [#579 spine](job-coordinator.md)) — driven by the Deploy panel's "Run over the cluster" action and a churn-shaped sim-Python program in the [governed Console](governed-console.md) — not an isolated single-node loopback. - [cloud-inspector.md](cloud-inspector.md) — the headed **Cloud Inspector** (`zetta::CloudProviderCatalog` + `zetta::CloudInspector` + `App::draw_cloud`): inspect a deployment target (local / on-prem / Kubernetes / AWS / GCP / Azure / OCI) behind a deny-by-default, ask-every-time consent gate that names exactly what an inspect would read/call. On consent it runs the provider's read-only commands via the shared `CommandRunner`, parses each vendor's JSON at a validated boundary into identity / regions / nodes (no creds read), and surfaces it in the panel + the `system.zetta_cloud_providers` / `system.zetta_cloud_status` tables.
- [provisioner.md](provisioner.md) — the `Provisioner` seam + node capability model (`zetta::NodeCapability`): provision N nodes against a capability spec / tear down / list; cores / GPU type+throughput / memory (ARC-13 / ENT-32, #373) — plus the `LocalProvisioner` given-hardware backend (uses existing cluster nodes, best-effort; teardown is a no-op; #374).
