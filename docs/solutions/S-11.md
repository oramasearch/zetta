# S-11 Next-Best-Action

S-11 chooses an eligible action for each customer at request time, including
no action, and returns it through the shared action integration layer. It is
runnable at all four catalogue levels. `create_solution` composes M-2 identity
resolution, M-1 predictive scoring, M-6 uplift evidence, M-8 action ranking,
and M-15 constrained exploration over a frozen decision snapshot.
`run_solution` arbitrates the candidate actions, protects the holdout, logs the
actual selection probability, delivers an acknowledged decision response,
records the ledger, updates guardrails, and feeds `get_roi_readout`.

Predictive response propensity is used only to rank actions. It is not causal
lift. Causal claims require the randomized uplift cells and M-6 evidence.

## Data contract

The source contains one row per customer/action candidate at the decision
cutoff. The snapshot key identifies the candidate row; the M-8 entity role
identifies the customer shared by those candidates.

| Role | Required | Meaning |
|---|---:|---|
| entity | yes | Stable customer identity shared across channels |
| candidate key | yes | Unique row key used to retain each customer/action candidate in the snapshot |
| action | yes | Integer action identifier, including any explicit no-action arm |
| label | yes | Matured per-action response in `[0,1]` |
| feature | yes | Numeric context available before the decision in every channel |
| value and cost | yes | Action value and cost used for expected net-value ranking |
| eligibility | yes | Numeric eligible flag consumed by M-8 and the policy |
| consent | yes | Explicit channel consent or suppression evidence |
| contact | yes | Cross-channel contact count and applicable cap |
| propensity | yes | Actual probability under the historical logging policy |
| interaction | yes | Count and timestamp for the time-based recommender holdout |
| channel | yes | Delivery channel associated with each candidate action |
| bandit | yes | Decision key, observed arm, and bounded reward for M-15 |
| uplift | yes | Treatment, outcome, and pre-treatment features for M-6 |

The caller also supplies the snapshot boundary, shared dataset contract,
connector destination and owner, and ROI economics. Delivery credentials are
write-only Run input. A source may use different column names by binding the
M-8 and M-15 hints explicitly.

## Levels

| Level | Native stages | Catalogue behavior |
|---:|---|---|
| 1 | M-2, M-1, M-6, M-8, M-15 | Single-channel batch decisions with protected measurement and exploration |
| 2 | level 1 | Request-time single-channel execution |
| 3 | level 2 | Cross-channel arbitration under shared constraints |
| 4 | level 3 | Long-horizon objective configuration |

Every level executes the same five registered native callbacks. The levels
describe the operating configuration; none substitutes a churn score for the
M-8 recommendation table. S-11 binds `decision_source` to M-8 `entity` and
`policy_score` output columns automatically.

## Defaults

The `recommended` tier starts at policy score zero and returns an A2
`decision_api_response`. A high-stakes owner can choose the configured A1
`high_stakes_review`; `no_action` remains A0. The lifetime contact cap is four,
and each delivered action is limited to one in a rolling seven-day window.
Eligibility, consent, and a remaining cross-channel contact allowance must all
be explicit. `excluded`, `do_not_contact`, or denied consent suppress action.
The default budget is 1,000 currency units and the kill switch is off. These
values are editable starter settings, not calibrated business recommendations.

Each customer is deterministically assigned to a permanent 10% holdout or to
equal `exploit` and `explore` cells. The explore cell is an experiment
exploration tier and uses the M-15 chosen arm and its logged probability. The
exploit cell uses the M-8 best eligible action and records selection probability
one. An explored arm that is not in the current eligible candidate set is
refused rather than delivered.

The named outcome is `net_value` over 30 days under the `uplift_cells` design.
Guardrails require zero consent violations, contact-cap violations, missing
propensities, and margin-floor violations, plus at least 0.95 action execution.
All five are observed by each completed S-11 Run.

## Run it

1. Create a Project and land candidate, historical outcome, and bandit reward
   rows.
2. Call `get_solution` with `{"solution":"S-11"}` and select a level.
3. Call `create_solution` with the snapshot, dataset, delivery, and ROI
   settings plus M-8 role hints. When the bandit decision key is not
   `decision_id`, set `M-15.decision_column`.
4. Call `run_solution` with the returned graph and optional delivery token,
   then poll `get_run`.
5. Query the M-8 recommendation table, M-15 decision-propensity table, final
   decision table, policy, experiment, monitor, action tasks, and ledger.
   Delivered payloads include selected action, channel, exploit/explore mode,
   actual selection probability, predictive propensity, and the
   `predictive_not_causal` interpretation.
6. Record matured `net_value` outcomes against ledger action IDs and call
   `get_roi_readout` after the outcome window closes.

Webhook, Salesforce, and HubSpot delivery use the shared idempotency, retry,
acknowledgement, dead-letter, kill-switch, holdout, and audit behavior.

## Correctness checks

`create_solution` and `run_solution` execute the same composed checks. Each
condition below is a refusal:

1. `s11_logged_propensity` requires M-8 historical logging propensities, its
   declared off-policy evaluation mode, M-15, and the durable decision
   propensity output. Missing or non-positive request-time probability rows
   fail the Run.
2. `s11_contact_consent` requires named consent, eligibility, contact-count,
   and contact-cap evidence, cross-channel enforcement, and M-8 hard
   eligibility/cap selection before an action reaches policy evaluation.
3. `s11_propensity_interpretation` requires
   `predictive_not_causal`, refuses a causal claim from predictive propensity,
   and requires M-6 randomized uplift evidence.

The planted-effect journey retains two channel candidates per customer,
executes all five native stages, verifies exploit and explore deliveries,
proves holdout, consent, and contact-cap suppression, reads every positive
M-15 propensity, records centered outcomes with a 0.18 effect, and asserts
that `get_roi_readout` recovers the effect inside its 95% confidence interval.

Boundary: this module adds no new JSON record format. It binds S-11 settings
into existing graph attributes, policy, experiment, monitor, action, ledger,
and ROI schemas. A live lake proof follows deployment of this branch.
