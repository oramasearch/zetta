# S-5 Demand Forecasting

S-5 forecasts demand by item, location, or another declared series, publishes
prediction intervals to planners, and routes the widest relative intervals to
an exception queue. It is runnable at all four catalogue levels.
`create_solution` composes native M-2, M-4, and M-3 stages, with M-5 added at
levels 3 and 4. `run_solution` materializes the caller's snapshot, executes the
registered methodology callbacks, applies the versioned policy and protected
holdout, delivers reports and tasks through action integration, records the
ledger, observes guardrails, and feeds `get_roi_readout`.

## Data contract

The caller lands ordered demand history and supplies these roles:

| Role | Required | Meaning |
|---|---:|---|
| time | yes | Ordered observation time and the inclusive snapshot cutoff |
| label | yes | Demand quantity to forecast |
| series | yes | Leaf item, location, or other independently forecast series |
| hierarchy | no | Ordered parent columns ending in the leaf series column; defaults to the leaf alone |
| identity | M-2 | Source, record ID, and name fields used to resolve records |
| feature | M-3 | Past-only numeric inputs used to describe forecast groups |
| event | levels 3–4 | Duration and event evidence for the attached M-5 timing stage |
| owner | for actions | Planner or queue owner; otherwise the delivery owner is used |

Each action row must explicitly pass `planner_owned`, `forecast_fresh`, and
`hierarchy_consistent`. `stockout_censored` and `override_locked` suppress an
exception task. Manual overrides carry an override reason so the audit
guardrail can distinguish explained and unexplained changes. The caller also
supplies the snapshot boundary, methodology role hints, delivery destination,
owner, and readout economics. Delivery credentials are write-only Run input.

M-4 reads the materialized snapshot directly. The downstream policy binds the
real M-4 `forecast` output table, uses `series` as the entity, and uses
`exception_score` as the score. That score is the interval half-width divided
by the larger of the absolute point forecast and one.

## Levels

| Level | Native stages | Behavior |
|---:|---|---|
| 1 | M-2, M-4, M-3 | Forecast table with intervals, seasonal-naive FVA, planner report, protected holdout, and governed exceptions |
| 2 | level 1 | Freshness-gated exception operation over the same registered callbacks |
| 3 | level 2 + M-5 | Event timing attached to the forecasting workflow |
| 4 | level 3 | Scenario-planning catalogue shape over the same runnable stages |

Every selected stage is built and run through its methodology registration.
No level substitutes an M-1 churn score table for the M-4 forecast output.

## Defaults

The policy has three interval-uncertainty tiers:

- `critical`: score at least 0.20, creating an A2 `exception_queue` task;
- `review`: score at least 0.05, creating the same governed task;
- `routine`: score at least 0.0, recording A0 `no_contact`.

Exception tasks have a one-day SLA. The lifetime cap is 52 tasks per series,
and the rolling cap is one task per seven-day window. The spending budget is
zero because the actions are reports and review tasks, not orders. The kill
switch is off. Planners retain approval over planning decisions; the module
does not release replenishment or override a plan.

The experiment assigns every series deterministically within its current tier.
Each critical, review, and routine tier has a 10% protected holdout probability;
the remaining series enter the `planner_report` treatment cell. Held-out
series receive neither an exception task nor a row in the delivered planner
report.

The monitor observes minimum forecast value added of 0, minimum interval
coverage of 0.75, maximum stale-forecast fraction of 0, maximum
stockout-censored fraction of 0.10, and maximum unexplained-override fraction
of 0. These are editable starter settings, not calibrated operating targets.

## Run it

1. Create a Project and land the demand-history table.
2. Call `get_solution` with `{"solution":"S-5"}` and select a level.
3. Call `create_solution` with the foundation request described in
   [executable-pipelines.md](executable-pipelines.md). Put M-3 and M-4 role
   hints in `sources.M-3` and `sources.M-4`. Put the ordered hierarchy in
   `sources.correctness.hierarchy_columns`.
4. Call `run_solution` with the returned graph and optional delivery token,
   then poll `get_run`.
5. Read the M-4 forecast table and parent decision table from the Run outputs.
   Read policy, assignments, guardrails, action tasks, planner publication,
   and ledger through their existing APIs.
6. Record `forecast_error` outcomes against ledger action IDs and call
   `get_roi_readout` after the outcome window closes.

Webhook, Salesforce, and HubSpot task delivery use the shared outbox,
idempotency, retry, acknowledgement, dead-letter, kill-switch, holdout, and
audit behavior. The exception payload carries series, forecast timestamp,
point forecast, lower and upper interval bounds, uncertainty score, owner,
SLA, tier, and decision cell. The planner report carries only non-held-out
forecast rows plus M-4 FVA and interval metrics.

## Correctness checks

`create_solution` and `run_solution` execute the same composed correctness
checks. Each condition below is a refusal:

1. M-4 must declare rolling-origin validation with at least two backtest folds.
   Random and row holdouts are refused.
2. Future covariates are refused. Forecast features must be strictly past
   target lags and rolling summaries at each forecast origin.
3. The hierarchy must name at least one column, end in the declared leaf
   series column, and use bottom-level-only forecasts so parent totals are
   derived by summing leaves.
4. M-2, M-4, and M-3 are mandatory at every level. Levels 3 and 4 also require
   M-5.

M-4 independently checks its temporal folds, past-only lag construction,
seasonal-naive baseline, interval configuration, and absence of probability
calibration.

## Measurement and proof

M-4 reports forecast value added against its seasonal-naive baseline and
empirical interval coverage. The solution readout labels the design `fva` and
does not turn the protected operational holdout into a causal ROI claim. Until
a design-specific FVA estimator is part of the readout, incrementality and ROI
remain explicitly non-claimable.

The native journey builds and runs S-5 over partitioned synthetic demand,
checks the real M-4 output binding, verifies that protected series receive no
task or report row, inspects interval-rich exception payloads, records planted
forecast errors, and verifies the readout states the FVA limitation. Live lake
proof is deferred until this branch is deployed.

Boundary: this module adds no new JSON format. It binds S-5 settings into the
existing graph attributes, policy, experiment, monitor, action, ledger, Run,
and ROI schemas.
