# B-8 IT & Security Operations

B-8 prioritizes operational and security risks, adds dependency context, and
advances authority only from investigation to approval to bounded containment.
It is runnable at all four catalogue levels. `create_solution` composes M-12
graph features and M-7 anomaly detection over one frozen snapshot.
`run_solution` applies the versioned response policy, protects permanent
holdouts, delivers approved actions through action integration, records the
ledger, observes guardrails, and feeds `get_roi_readout`.

The primary decision source is M-7's real `anomaly table`, using `row` as the
entity key and `score` as risk. M-12 supplies time-bounded relationship context;
it does not replace the anomaly score with an unrelated output.

## Data contract

The caller lands ordered security or operations observations with these roles:

| Role | Required | Meaning |
|---|---:|---|
| entity | yes | Stable asset, identity, or service key |
| time | yes | Event and relationship chronology before the decision cutoff |
| feature | yes | Finite numeric telemetry, relationship weight, and risk evidence |
| group | yes | Dependency or identity relationship destination |
| owner | yes | Accountable operations or security response owner |
| eligibility | yes | Approved playbook, containment permission, dependency scope, and affected-asset count |
| label | evaluation only | Confirmed incident or impact, never a decision-time feature |

Action rows must explicitly pass `eligible`, `owner_assigned`,
`approved_playbook`, `containment_allowed`, and `dependency_scope_known`.
`affected_assets` must be no greater than one. `manual_only`,
`protected_asset`, or `active_incident` blocks delivery. Missing evidence also
blocks delivery. The caller supplies the snapshot cutoff, M-7 anomaly settings,
M-12 relationship roles, response destination, fallback owner, and readout
economics. Delivery credentials remain write-only Run input.

M-12 reads the entity, dependency, edge-weight, time, and optional incident
label columns. Edges after `prediction_time` are excluded. M-7 requires finite
numeric features and an exact integer `alert_budget`; a contamination fraction
is not accepted as a substitute.

## Levels

| Level | Native stages | Behavior added |
|---:|---|---|
| 1 | M-12, M-7 | Prioritized alerts and A0 investigation recommendations |
| 2 | M-12, M-7 | A1 containment approval tasks |
| 3 | M-12, M-7 | Single-asset A2 containment inside an approved playbook |
| 4 | M-12, M-7 | Dependency-aware bounded containment with the same A2 ceiling |

Every level uses the registered M-12 and M-7 callbacks. Increasing the level
changes the selected policy action; it does not introduce a foreign runtime or
raise the authority ceiling above A2.

## Defaults

The policy starts with `critical` at score 0.8, `elevated` at 0.4, and
`advisory` at 0.0. Advisory and unflagged rows select `no_action`. The two
response tiers select `investigation_recommendation` at level 1,
`containment_approval` at level 2, and `bounded_containment` at levels 3 and 4.
Those actions are A0, A1, and A2 respectively.
Each level's live tier allowlist contains only its selected action and
`no_action`, so evidence cannot request a higher-authority action indirectly.

`bounded_containment` has a five-minute SLA and becomes approval-required above
one affected asset. The eligibility rule independently refuses more than one
affected asset, so the default automatic path cannot cross the approved bound.
The alert and lifetime action cap is 10, each entity is limited to one response
per day, monetary spend is zero, and the kill switch is off but present in the
live policy.

Each severity tier has a deterministic permanent 10% holdout; remaining rows
enter the `operational_response` treatment cell. Measurement uses the named
`incident_avoided` outcome over 30 days. The readout estimates the protected
difference and reports its confidence interval. Customer-supplied value and
investment settings remain separate from engineering readiness.

Guardrails bound alert volume at 10, containment scope at one affected asset,
unapproved containment and kill-switch bypass at zero, and action execution at
a minimum 0.95. The Run observes all five values.

## Run it

1. Create a Project and land a partitioned, time-ordered event and relationship
   table.
2. Call `get_solution` with `{"solution":"B-8"}` and select an integer level.
3. Call `create_solution`. Put exact-budget anomaly settings in `sources.M-7`,
   edge roles and cutoff in `sources.M-12`, and snapshot, dataset, delivery, and
   ROI settings in `foundation`.
4. Use dataset feature columns whose first two entries are the dependency and
   edge-weight columns required by M-12. Include the numeric telemetry columns
   M-7 will score.
5. Call `run_solution` with the returned graph and optional delivery token,
   then poll `get_run`.
6. Read the decision table, policy, experiment, monitor, action tasks, and
   ledger. A containment task includes the asset, dependency, anomaly score and
   threshold, affected-asset count, playbook and dependency evidence, selected
   authority boundary, decision cell, and kill-switch check.
7. Record `incident_avoided` outcomes against ledger action IDs and call
   `get_roi_readout`.

Webhook delivery uses the shared idempotency, retry, acknowledgement,
dead-letter, holdout, audit, and kill-switch behavior.

## Correctness checks

`create_solution` and `run_solution` execute the same composed correctness
checks. Each condition below is a refusal:

1. The alert budget must be a positive integer with a reporting window and
   owner. M-7 must enforce the same exact budget, and both M-7 and M-12 must be
   present.
2. Authority must declare A0 investigation, A1 approval, and only bounded A2
   containment. The action selected for levels 1–4 must match that progression.
3. A configured boolean kill switch must be present and declared as a hard
   delivery stop.
4. Automatic containment must name only `bounded_containment`, require an
   approved positive affected-asset bound, and require playbook and dependency
   scope evidence.

Before decisions, the live policy is checked again. It must retain the boolean
kill switch, the A0/A1/A2 action mappings, the selected level action, the
single-asset approval and eligibility bounds, and the playbook, containment,
and dependency predicates. Any extra A2 action or broader containment bound is
refused. When the kill switch is active, the policy engine blocks delivery.

The automated journey plants risk spikes in a partitioned synthetic event
table. It builds and runs level 3, excludes a future event, executes both native
methodologies, verifies the ten-alert ceiling, protects holdouts, inspects every
bounded action payload, observes all guardrails, records a planted 0.16
incident-avoidance effect, and asserts that the estimate and confidence
interval recover it.

The module's recorded promotion condition remains a go-to-market gate: offer it
as an attach-on after multiple modules prove the shared governed-operations
pattern. That condition does not change `runnable: true` engineering status.

Boundary: this module adds no new JSON format. It binds B-8 settings into the
existing graph attributes, policy, experiment, monitor, action, ledger, and ROI
schemas. A live lake proof follows deployment of this branch.
