# S-6 Replenishment & Inventory Action

S-6 turns demand history into forecast-driven purchase or transfer proposals,
solves the constrained replenishment plan, and routes the result from a manual
draft through owned ERP work to bounded automatic release. It is runnable at
all four catalogue levels. `create_solution` composes M-4 forecasting and M-16
optimization, with M-5 time-to-stockout from level 3. `run_solution` executes
those native callbacks before policy, holdout protection, action delivery,
ledger recording, monitoring, and ROI readout.

## Data contract

The caller lands bounded demand history plus the latest inventory and ordering
evidence for each item-location:

| Role | Required | Meaning |
|---|---:|---|
| entity | yes | Stable numeric item-location key used by forecast, snapshot, policy, and ledger |
| time | yes | Ordered demand timestamps and the inclusive inventory cutoff |
| label | yes | Numeric demand quantity for M-4; M-5 also needs a binary event indicator |
| variable | yes | Order or transfer variable with lower and upper bounds |
| constraint | yes | Capacity, budget, lead-time, and service constraints with coefficients and right-hand sides |
| scenario | yes | Scenario or quantile marker; M-16 refuses an unqualified point forecast |
| cost | yes | Unit, order, and working-capital cost used by policy and measurement |
| owner | for routed work | Planner or buyer accountable for the ERP task |

Every decision row must explicitly supply `eligible`,
`lead_time_confirmed`, `inventory_hold`, `supplier_blocked`,
`order_quantity`, `cost`, and the observed guardrail fields. Missing
eligibility evidence blocks action. The caller also supplies the snapshot
cutoff, M-4 history table and column roles, delivery destination, owner, and
ROI economics. Delivery credentials remain write-only Run input.

## Levels

| Level | Native stages | Action behavior |
|---:|---|---|
| 1 | M-4 + M-16 | Forecast and constrained plan; `draft_order` is A0 and remains a recommendation |
| 2 | level 1 | `erp_replenishment_task` is A2 and enters the action outbox with an owner and SLA |
| 3 | level 2 + M-5 | Adds censoring-aware time-to-stockout evidence |
| 4 | level 3 | `release_order` is A2 only inside the automatic quantity bound and all policy constraints |

M-4 reads the configured bounded history table. M-16 and M-5 read the latest
item-location snapshot. The decision source is M-4's real `forecast` output.
S-6 sums the forecast points across the declared lead-time horizon to produce
one replenishment-demand score per item-location; it does not substitute an
M-1 score table.

## Defaults

The `replenish` tier begins at a lead-time demand score of 1. Level 1 selects
`draft_order`, levels 2–3 select `erp_replenishment_task`, and level 4 selects
`release_order`. The `no_order` tier records no contact. Drafts are A0; ERP
tasks and in-bound releases are A2. A release above 100 units becomes A1 and
waits for approval. Quantities above the hard 500-unit eligibility bound are
blocked. Policy changes remain owner-governed.

Eligibility requires `eligible == true`, `lead_time_confirmed == true`, and
`order_quantity <= 500`. Inventory holds and supplier blocks suppress action.
The default budget is 10,000 currency units, the lifetime cap is 52, the
rolling cap is one action per 30 days, and the kill switch is off. These are
editable starter settings, not calibrated purchasing recommendations.

Each item-location is assigned deterministically to a permanent 10% holdout or
the `replenishment_action` treatment cell. The named outcome is
`service_level` over 30 days. Guardrails cover replenishment spend, minimum
service level, inventory exposure, order volatility, and unapproved orders
above the automatic bound. Every guardrail is observed by the Run.

## Run it

1. Create a Project and land the bounded demand and inventory table.
2. Call `get_solution` with `{"solution":"S-6"}` and choose a level.
3. Call `create_solution` with the shape in
   [executable-pipelines.md](executable-pipelines.md). Configure M-4 with the
   history table, time, target, series, and a horizon that covers lead time.
4. Set `foundation.decision_source` to methodology `M-4`, output `forecast`,
   entity column `series`, and score column `point_forecast`. Supply the latest
   snapshot, dataset roles, ERP or webhook destination, and ROI economics.
5. Call `run_solution`, poll `get_run`, then read decisions, policy,
   experiment, monitor, tasks, ledger, and child Run outputs.
6. Record the named `service_level` outcome against each ledger action and call
   `get_roi_readout` after the outcome window closes.

The action payload carries item, location, supplier, proposed quantity, lead
time, service target, cost, owner, SLA, decision cell, and policy version.
Webhook, Salesforce, and HubSpot destinations use the shared replicated
outbox, idempotency, retry, acknowledgement, dead-letter, holdout, kill-switch,
and audit behavior.

## Correctness checks

`create_solution` and `run_solution` execute the same composed correctness
checks. Each condition below is a refusal:

1. Service level must be in `(0, 1]`, the budget cap must be positive, and the
   plan must name both service and budget constraints. M-16 must independently
   verify constraints.
2. Lead time must be positive and backed by frozen snapshot evidence. The M-4
   forecast horizon must cover that lead time.
3. Automatic and hard order bounds must be positive and ordered. Releases
   above the automatic bound must require A1 approval; the hard bound must be
   enforced.
4. Every level requires M-4 and M-16. Levels 3–4 require M-5. The selected
   level must carry the matching action authority, and level 4 must carry the
   kill-switch setting.

The journey
`SolutionJourney.ReplenishmentReleasesBoundedOrdersAndRecoversPlantedEffect`
runs level 4 over partitioned synthetic demand history. It verifies the real
methodology outputs, protected holdouts, bounded release payloads, observed
guardrails, ledger outcomes, and recovery of the planted 0.12 service-level
effect inside its 95% confidence interval.

Boundary: this module adds no new replicated record or wire format. It adds an
optional action approval field to the existing policy schema and binds S-6
settings into existing graph, policy, experiment, monitor, action, ledger, and
ROI records. Live lake proof follows deployment of this branch.
