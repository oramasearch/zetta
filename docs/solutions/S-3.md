# S-3 Customer Lifetime Value

S-3 predicts net customer value over a stated future horizon and turns that
prediction into governed audience and budget decisions. It is a runnable
solution module: `create_solution` composes the native M-2, M-1, and M-3
pipeline at level 1, while `run_solution` executes the snapshot, value
regression, policy, permanent holdout, action integration, ledger, monitor,
allocation report, and ROI readout.

The primary decision source is M-1's real
`clv_results.lifetime_value_*` output. Each row names the stable entity and its
`predicted_value`; the policy does not substitute churn probability or a
fabricated score. The distributed squared-error GBDT is registered as a
regressor and reports RMSE and MAE, including held-out values when configured.

## Data contract

The caller lands one point-in-time customer table and supplies these roles:

| Role | Required | Meaning |
|---|---:|---|
| entity | yes | Stable customer or account key counted once |
| label | yes | Net future value observed over the declared horizon |
| time | yes | Snapshot cutoff, feature cutoff, and cohort observation time |
| feature | yes | Pre-cutoff value, cost, engagement, and tenure inputs |
| tenure | yes | Customer age used to censor immature value labels |
| margin | yes | Current margin evidence for the policy floor |
| consent | yes | Audience consent and channel eligibility |
| treatment | levels 3–4 | Audience, service, or budget intervention and outcome |
| owner | for routed work | Audience or budget owner |
| duration and event | level 2 | Follow-up duration and event indicator for M-5 |

Action evidence must include `consent`, `channel_eligible`, `margin`,
`do_not_target`, and `account_closed`. Missing eligibility evidence or a true
exclusion blocks the action. The caller also supplies the snapshot boundary,
delivery destination and owner, and ROI currency/economics. Delivery
credentials remain write-only run input.

The default horizon is 365 days. Override it in
`sources.M-1.value_horizon_days`; the M-1 model target, correctness profile,
measurement window, and recorded outcomes must describe the same business
horizon. A customer below the configured minimum observed tenure is
right-censored rather than treated as having complete lifetime value.

## Levels

| Level | Native stages | Behavior added |
|---:|---|---|
| 1 | M-2, M-1, M-3 | Entity resolution, value regression, segments, governed audience sync, budget approvals, permanent value-band holdouts, allocation report, and readout |
| 2 | level 1 + M-5 | Censoring-aware survival horizon for customer tenure |
| 3 | level 2 + M-6 | Causal audience and budget allocation from randomized intervention data |
| 4 | level 3 | Governed cross-channel budget policy using the same composed native stages |

All four levels compose and pass the module gate. `get_solution` returns their
integer `level`, `name`, and `description`; pass the selected integer to
`create_solution.level`. Level 2 and above require the additional methodology
roles shown in the table rather than inventing missing event or treatment data.

## Executable defaults

The policy has three predicted-value bands:

| Band | Minimum predicted value | Default decision | Authority |
|---|---:|---|---|
| strategic | 1,000 | `budget_reallocation` | A1 approval |
| growth | 500 | `audience_sync` | A2 |
| standard | 0 | `no_contact` | A0 |

Audience sync and budget reallocation allow at most one action in a rolling
30-day window, with a lifetime contact cap of 12. Budget changes always remain
pending A1 approval. The per-policy budget ceiling is 10,000 currency units.
Eligibility requires consent, channel eligibility, and margin of at least 0.2;
`do_not_target` and `account_closed` suppress action. The kill switch is off.

Every value band receives an independent deterministic 10% holdout. Protected
entities are recorded as `no_contact`, never delivered to an audience or budget
connector, and remain available for measurement. Treatment cells are
`audience_sync` and `budget_reallocation`; the named outcome is `net_value` in
the configured currency over 365 days.

The monitor records consent violations, margin violations, discount-fairness
gap, budget utilization, and cohort-calibration error. A webhook run delivers
actionable audience rows with predicted value and horizon and publishes a
customer-lifetime-value allocation report. Budget reallocations remain in the
ledger as pending approvals until an authorized action flow approves them.

These thresholds and limits are editable starter configuration, not calibrated
customer recommendations, prices, or return claims.

## Run it

1. Create a project and land the customer-value table.
2. Call `get_solution` with `{"solution":"S-3"}` and choose a level.
3. Call `create_solution` with the snapshot, dataset, delivery, and ROI
   foundation described in [executable-pipelines.md](executable-pipelines.md).
   Set the continuous label and horizon under `sources.M-1`; put optional gate
   overrides under `sources.correctness`.
4. Call `run_solution` with the returned graph and optional delivery token, then
   poll `get_run`.
5. Read decisions from `solution_results`, value predictions from
   `clv_results`, assignments with `get_experiment`, guardrails with
   `get_monitor`, and action/report evidence with `list_ledger` and the action
   integration read-backs.
6. Record `net_value` against each action ID after the horizon closes, including
   protected holdouts, then call `get_roi_readout`.

The end-to-end journey uses a partitioned synthetic cohort with a planted
75-currency-unit treatment effect. It excludes a post-cutoff customer, creates
and runs S-3, verifies that protected entities are not delivered, records
centered treated and holdout outcomes, and requires the readout to recover 75
inside its 95% confidence interval.

## Correctness checks

`create_solution` and `run_solution` execute the same composed gate. Each rule
below is a hard refusal:

1. `s3_short_tenure_censoring` requires a named tenure field, a positive
   minimum observed tenure, right-censor handling, and explicit application to
   training labels. Level 2 and above must include M-5.
2. `s3_value_horizon` requires a positive horizon and nonempty value label. The
   M-1 model must use squared-error regression with that exact target and
   horizon.
3. `s3_entity_accounting` requires M-2, a stable entity key,
   `one_value_per_entity` aggregation, and duplicate refusal. Values cannot be
   summed across customer or account identities.

The tests build every level and mutate each adaptation to prove its named bad
case is refused.
