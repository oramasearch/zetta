# S-10 Fraud & Financial-Crime Decisioning

S-10 scores authorization requests before the response leaves the decision
path, combines point-in-time transaction signals with relationship-graph
features, applies a governed approve/challenge/review policy, and sends review
work to case management. It is a runnable solution module: `create_solution`
builds M-2 identity resolution, M-12 graph features, M-1 fraud scoring, and the
optional M-5 time-to-event stage over the shared snapshot, policy, experiment,
action, ledger, monitor, and ROI foundations.

The M-1 stage writes a real `fraud_results.authorization_scores_*` table with
`transaction` and `fraud_score` columns. The solution binds decisions to that
output rather than the retention score table used by the generic M-1 example.

## Data contract

The caller lands one current row per authorization request. The snapshot keeps
only the latest row visible at the configured cutoff.

| Role | Required | Meaning |
|---|---:|---|
| entity | yes | Stable transaction or authorization-request id |
| label | yes | Matured fraud, dispute, or case disposition |
| time | yes | Request time, graph-edge time, and label-maturation chronology |
| feature | yes | Numeric request-time transaction, device, and behavioral inputs |
| group | yes | Account, device, merchant, and counterparty relationship edge |
| propensity | yes | Logged authorization or exploration propensity |
| owner | yes | Case queue or investigation owner |

The executable default expects `decision_propensity` and at least one named
graph feature, `graph_page_rank`, in both the training and authorization
feature lists. Policy evidence must explicitly include `eligible`,
`account_open`, `request_time_features_current`,
`graph_features_current`, `excluded`, and `manual_authorization_only`.
Missing eligibility evidence blocks action.

M-12 interprets the dataset entity as the source node, the first two feature
columns as destination node and non-negative edge weight, the dataset time
column as edge time, and the label as the source-node label. Put those columns
first in `feature_columns`, followed by the remaining numeric fraud features.

## Levels

| Level | Native stages | Behavior added |
|---:|---|---|
| 1 | M-2, M-12, M-1 | Post-event review priority, graph context, protected experiment cells, governed decisions, and case tasks |
| 2 | level 1 | Request-time approve, challenge, and review bands on the same native stages |
| 3 | level 2 + M-5 | Account-takeover timing and time-to-event context |
| 4 | level 3 | Financial-crime case assistance with the same approval boundary |

Every level builds through the registered methodology callbacks. Levels 3 and
4 require M-5; all levels require M-1, M-2, and M-12.

## Defaults

The policy begins with three score bands:

- `critical` at 0.9 creates an A2 `fraud_review_task` with a 15-minute SLA;
- `elevated` at 0.65 returns an A2 `challenge` decision;
- `standard` at 0 returns an A2 `approve` decision.

Critical decisions may be changed to `challenge` or `block`; `block` is A1 and
therefore requires approval. One decision per transaction is allowed in a
one-day window. The default spending budget is zero and the kill switch is
off. Operators replace these starter thresholds with calibrated settings and
may tune only values their policy explicitly exposes.

The deterministic experiment protects 10% of each score band as holdout. The
remaining requests enter named `champion`, `challenger`, or `exploration`
cells. Protected requests record a no-action ledger row and never reach the
connector. The measurement design is `champion_challenger`; it observes
`fraud_loss` in currency over 45 days. The monitor records fraud-loss rate,
false-decline rate, challenge rate, review-queue rate, and action-execution
rate.

## Run it

1. Create a project and land the authorization table.
2. Call `get_solution` with `{"solution":"S-10"}` and choose level 1–4.
3. Call `create_solution` with an explicit snapshot, dataset contract,
   delivery destination/owner, and ROI economics. Put M-12 edge-column hints
   under `sources.M-12`.
4. Call `run_solution` with the returned graph and an optional write-only
   connector token, then poll `get_run`.
5. Read `fraud_results.authorization_scores_*`, the parent decision table,
   experiment assignments, action tasks, ledger rows, and monitor state.
6. Record each matured `fraud_loss` against its ledger action id and call
   `get_roi_readout` after the outcome window closes.

Request-time decisions and review tasks both use the shared action outbox,
connector, retry, acknowledgement, idempotency, dead-letter, kill-switch, and
audit paths. Payloads carry the authorization decision, transaction, amount,
account, merchant, counterparty, graph evidence, decision cell, case owner, and
whether the delivery is a case task.

## Correctness checks

`create_solution` and `run_solution` apply the same bound checks. Each is a
hard refusal:

1. `s10_label_delay` requires a named fully matured label and an observed delay
   at least as long as the configured minimum.
2. `s10_declined_selection_bias` requires declined requests in the learning
   population, logged exploration propensities, and below-the-line audit
   evidence. The propensity column must be a training feature.
3. `s10_request_time_feature_parity` requires exact training/authorization
   feature equality, named graph features in that set, bounded freshness, and
   a graph cutoff no later than the decision.
4. `s10_level_composition` requires M-1, M-2, and M-12 at every level and M-5
   at levels 3 and 4. M-12 also retains its native edge-time correctness check.

The planted-effect journey runs build → run → decide → act, verifies protected
holdouts and both authorization/case payloads, records centered synthetic
fraud-loss outcomes with a `-0.12` effect, and checks that the ROI readout's
estimate and 95% confidence interval recover it.

Boundary: this module adds no new JSON format. It binds S-10 settings into the
existing solution foundation, policy, experiment, action, ledger, monitor, and
readout records. A live lake proof is a post-deploy validation.
