# S-7 KPI Anomaly & Driver Analysis

S-7 detects KPI changes against a causal seasonal baseline, ranks candidate
drivers, and routes bounded evidence to an owned decision forum. It is runnable
at all four catalogue levels. `create_solution` composes M-7 anomaly detection,
M-1 supervised driver context, M-3 segmentation, and optional M-4 forecast
context over one frozen snapshot. `run_solution` applies the versioned forum
policy, protects holdout entities, delivers through action integration, records
the decision log and outcome ledger, updates guardrails, and feeds
`get_roi_readout`.

Driver rankings are associations, not causal attributions. Every forum task and
published report carries that caveat. The primary decision source is M-7's real
`anomaly table`; S-7 does not substitute M-1 churn scores.

## Data contract

The caller lands ordered KPI history and supplies these roles:

| Role | Required | Meaning |
|---|---:|---|
| feature | yes | KPI value and numeric candidate-driver observations |
| time | yes | Ordered KPI period used by strictly prior seasonal windows |
| entity | yes | Stable observation, business-unit, or segment key |
| owner | yes | Decision-forum owner for routed evidence |
| permission | yes | Evidence that the forum may see sensitive driver names |
| label | evaluation only | Confirmed anomaly used to assess alerts, never to fit them |

Action rows must explicitly pass `eligible`, `forum_owner_assigned`, and
`sensitive_driver_access`. `suppressed` blocks delivery. The caller also
supplies the snapshot boundary, M-7 seasonality and alert-budget settings,
dataset roles, forum destination, fallback owner, and readout economics.
Delivery credentials remain write-only Run input.

The M-7 configuration uses `mode: kpi_time_series`, the ordered time column,
and finite numeric feature columns. Its seasonal period, trend window, residual
window, and cycle count must form a causal history. When M-3 receives a time
column, its numeric `as_of` must name the end of the prepared dataset.

## Levels

| Level | Native stages | Behavior added |
|---:|---|---|
| 1 | M-7, M-1, M-3 | Seasonal anomaly report, candidate-driver context, protected forum routing, and decision log |
| 2 | level 1 | Expanded candidate-driver forum workflow under the same native callbacks |
| 3 | level 2 + M-4 | Rolling-origin forecast context with a seasonal-naive baseline |
| 4 | level 3 | Cross-module executive-review option under A1 approval |

Every level is built from registered methodology callbacks. Levels 3 and 4
require M-4 and retain M-7 as the decision source.

## Defaults

The policy starts with a `critical` score floor of 0.8 and an `anomaly` floor of
0.0. Flagged rows in both tiers select `decision_forum_report`, an A2 action with
a one-day SLA. Critical rows may be changed to `executive_review`, an A1 action
with a four-hour SLA. Unflagged, excluded, capped, pending, and protected rows
are recorded as `no_contact`.

The alert and lifetime contact cap is 12. Each entity is limited to one routed
action in a rolling seven-day window. Default spend is zero and the kill switch
is off. The experiment assigns each tier deterministically to a permanent 10%
holdout or the `forum_routed` treatment cell.

Guardrails bound alert volume at 12, false-escalation rate at 0.25, sensitive
driver access violations at zero, causal-claim violations at zero, decision
closure at a minimum 0.9, and action execution at a minimum 0.95. The Run
observes alert volume, access and claim violations, and execution. Metrics that
depend on later forum outcomes remain unobserved until evidence is recorded.

Measurement is phased and names `decision_adopted` over 30 days. The current
readout reports treatment and protected evidence but refuses causal
incrementality and ROI claims until a module-specific phased estimator ships.
That refusal is intentional: a planted difference in forum adoption does not
turn an observational phased rollout into a causal estimate.

## Run it

1. Create a Project and land an ordered KPI history table.
2. Call `get_solution` with `{"solution":"S-7"}` and select an integer level.
3. Call `create_solution` with the request shape in
   [executable-pipelines.md](executable-pipelines.md). Put anomaly settings in
   `sources.M-7`, segmentation roles in `sources.M-3`, and forecast roles in
   `sources.M-4` for levels 3 and 4.
4. Set `foundation.decision_source` to methodology `M-7`, entity column `row`,
   score column `score`, and output name `anomaly table`.
5. Call `run_solution` with the returned graph and optional delivery token,
   then poll `get_run`.
6. Read the decision table, policy, experiment, monitor, forum tasks, published
   report, and ledger. The task includes period, score, threshold, candidate
   drivers, caveat, owner, decision cell, and decision-log requirement.
7. Record `decision_adopted` outcomes against ledger action IDs and call
   `get_roi_readout`. Treat the phased result as descriptive while it is marked
   non-claimable.

Webhook delivery uses the shared idempotency, retry, acknowledgement,
dead-letter, kill-switch, holdout, and audit behavior. One action-integration
report summarizes the bounded alerts, candidate drivers, caveat, and durable
decision log.

## Correctness checks

`create_solution` and `run_solution` execute the same composed correctness
checks. Each condition below is a refusal:

1. Driver attribution must be declared associational, causal claims must be
   disabled, and a nonempty caveat must be required.
2. The forum alert budget must be a positive integer with a window and owner.
   M-7 must use exact `alert_budget` selection with the same number; a
   contamination fraction or mismatched cap is refused.
3. M-7 must use KPI time-series mode, causal windows, and a named time role.
   The seasonal period, trend window, residual window, and cycle count must
   provide sufficient strictly prior history.
4. M-7, M-1, and M-3 are mandatory at every level. Levels 3 and 4 also require
   M-4 with rolling-origin validation and a seasonal-naive baseline.

The automated journey plants seasonal KPI spikes and correlated driver spikes
in a partitioned table. It builds and runs S-7, excludes a future observation,
verifies exactly 12 bounded alerts, protects permanent holdouts, inspects forum
tasks and the report decision log, records a planted adoption difference, and
asserts that the phased readout preserves the evidence while declining causal
and ROI claims.

Boundary: this module adds no new JSON format. It binds S-7 settings into the
existing graph attributes, policy, experiment, monitor, action, report, ledger,
and ROI schemas. A live lake proof follows deployment of this branch.
