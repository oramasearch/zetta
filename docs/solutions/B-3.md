# B-3 Ticket Triage & Service Automation

B-3 classifies service tickets against a customer-owned taxonomy, routes
confident tickets to an owned queue, and adds a draft reply at levels 2–4.
Low-confidence and new-type tickets explicitly abstain. Ticket closure is
available only as an A1 recommendation that requires human approval.

The module is runnable at all four levels. `create_solution` composes native
M-10 language classification and M-19 label-efficiency stages with a frozen
snapshot, versioned policy, permanent holdout, action integration, ledger,
monitor, and ROI readout. `run_solution` uses M-10's real `embeddings` output:
`chunk_id` is the decision entity and `classifier_confidence` is the score.

The catalogue retains its go-to-market condition: promotion for customer
offering requires enough ticket volume and a service organization that owns or
funds its taxonomy. That condition does not change engineering runnability.

## Data contract

| Role | Required | Meaning |
|---|---:|---|
| entity | yes | Stable integer ticket identifier used by both the snapshot and M-10 |
| text | yes | Governed ticket text supplied to the local M-10 checkpoint |
| label | yes | Customer-owned ticket-type label for the language head and M-19 evaluation |
| feature | yes | Numeric M-19 features used by active learning and weak supervision |
| time | yes | Observation time used by the point-in-time snapshot |
| taxonomy | yes | Queue, version, current-version flag, and customer-ownership evidence |
| owner | for routing | Queue owner; otherwise the configured delivery owner is used |
| resolution | for measurement | Named `resolution_quality` outcome recorded after the decision |

Every decision row must contain `service_eligible`,
`taxonomy_owned_by_customer`, `taxonomy_version_current`, `new_ticket_type`,
and `suppressed`. Missing eligibility evidence blocks action. A true new-type
flag selects `abstain` and also contributes to the drift monitor.

## Levels

| Level | Native stages | Behavior |
|---:|---|---|
| 1 | M-10, M-19 | Classify and route confident tickets; abstain below the governed threshold |
| 2 | M-10, M-19 | Add a draft reply to the routed queue task |
| 3 | M-10, M-19 | Add service-policy constraints while retaining the same approval boundary |
| 4 | M-10, M-19 | Add monitored service automation; closure still requires A1 approval |

Both methodologies run at every level. M-19 writes the label queue and weak
labels used to improve customer-owned taxonomy coverage. It does not replace
M-10's decision score.

## Executable defaults

The starter confidence threshold is 0.6 and may be configured from 0.5 through
0.95. A confident level-1 ticket selects `route_ticket`; levels 2–4 select
`route_and_draft`. Both are A2 with a one-hour SLA. `abstain` is A0.
`close_ticket` is A1 at every level and is never a default tier action. The
policy permits one service action per ticket per day and has no monetary spend.

The experiment protects 10% of assignments and places the remainder in the
`service_routed` treatment cell. Measurement uses the named
`resolution_quality` outcome over 30 days. The monitor records maximum
misroute rate 0.1, minimum resolution quality 0.8, maximum abstention rate 0.5,
maximum new-ticket-type rate 0.1, zero unapproved automatic closures, and
minimum action-execution rate 0.95. These values are editable starter settings,
not calibrated customer recommendations.

## Run it

Create a project, land the ticket table, and create a native M-10 checkpoint.
Pass methodology-specific run settings under the corresponding source entry;
the solution runner forwards each entry only to that methodology callback.

```json
{
  "project": "ticket triage",
  "solution": "B-3",
  "level": 4,
  "sources": {
    "source": "service",
    "database": "service",
    "table": "tickets",
    "M-10": {
      "embedder_directory": "/approved/checkpoints/minilm",
      "text_column": "text",
      "top_k": 1,
      "minimum_relevance": -1.0
    },
    "M-19": {
      "labelling_functions": [
        {
          "name": "urgent-ticket",
          "column": "urgency",
          "operator": "greater_equal",
          "value": 0.5,
          "label": 1,
          "otherwise_label": 0
        }
      ]
    },
    "correctness": {
      "minimum_confidence": 0.6,
      "taxonomy_owned_by_customer": true,
      "taxonomy_owner": "service-operations",
      "taxonomy_version": "customer-v42",
      "closure_approval_required": true,
      "new_ticket_type_monitoring": true,
      "maximum_new_ticket_type_fraction": 0.1
    }
  },
  "foundation": {
    "snapshot": {
      "database": "service",
      "source_table": "tickets",
      "target_table": "tickets_snapshot",
      "entity_column": "entity_id",
      "time_column": "observed_at",
      "as_of": "2026-09-01T00:00:00.000Z"
    },
    "dataset": {
      "entity_column": "entity_id",
      "label_column": "label",
      "feature_columns": ["urgency", "billing_signal"]
    },
    "delivery": {
      "kind": "webhook",
      "endpoint": "https://service.example.test/tasks",
      "owner": "service-operations"
    },
    "roi_model": {
      "value_per_outcome": 50,
      "investment": 100,
      "currency": "USD"
    }
  }
}
```

Call `run_solution` with the returned graph and optional write-only delivery
token, then poll `get_run`. Read decisions from `solution_results`, assignments
with `get_experiment`, delivery evidence with the action and ledger read-backs,
and observed bounds with `get_monitor`. Record `resolution_quality` against
each ledger action and call `get_roi_readout` after the outcome window closes.

The connector payload contains ticket ID, customer queue, draft reply,
taxonomy version, classification confidence, and an explicit human-close-
approval flag. Protected, excluded, low-confidence, new-type, and A1-pending
decisions never reach the connector.

## Correctness checks

`create_solution` and `run_solution` execute these B-3 refusals:

1. `b3_abstention_threshold` requires a finite confidence threshold in `(0, 1]`,
   requires policy and M-10 to use the same value, and requires A0 `abstain`.
2. `b3_customer_taxonomy` requires a named, versioned, customer-owned taxonomy,
   queue column, unmapped-ticket abstention, and policy-enforced ownership and
   current-version evidence.
3. `b3_closure_approval` requires `close_ticket` to remain A1. Runtime policy
   validation repeats this check before decisions execute.
4. `b3_new_ticket_type_drift` requires a bounded drift fraction, active
   monitoring, hard new-type exclusion, and abstention.
5. `b3_level_composition` requires levels 1–4 to contain runnable M-10 language
   and M-19 label-efficiency stages.

Unit tests mutate every condition and require its named refusal. The synthetic
journey builds level 4, runs both methodologies, verifies abstention and holdout
protection, inspects queue/draft action payloads and all six guardrails, records
a planted 0.16 resolution-quality effect, and requires the estimate and its 95%
confidence interval to recover that effect.
